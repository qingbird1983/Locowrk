# 规范 03：文档规范（文档先行）

- 状态：定稿
- 日期：2026-10-28

## 1. 文档先行流程（硬规则）

1. 阶段开工前置：该阶段 phase 文档 + 其引用的设计文档状态 = **定稿**。
2. “定稿”判定：内容完整、验收场景可执行、遗留问题逐条列出或有归属。
3. 所有者不审技术细节，但拥有**知情权与叫停权**：阶段开工/收尾必须反映在看板与 CHANGELOG。
4. 实现中发现设计有误：先改文档/ADR（说明为什么错、改成什么），再改代码；禁止“代码先行为主”。

## 2. 文档头与状态

每篇文档头部包含：

```markdown
- 状态：草稿 | 评审中 | 定稿
- 日期：YYYY-MM-DD（最近定稿/更新日）
- 关联：相关 ADR / 文档链接
```

- 状态变更必须同步 `docs/README.md` 清单表与 CHANGELOG。
- 定稿文档可修订：小修直接改并更新日期；语义级变更须在文内注明“YYYY-MM-DD 修订：……”，不可逆项另写 ADR。

## 3. 文档类型与归属

| 类型 | 目录 | 规则 |
|---|---|---|
| 决策记录 ADR | `docs/adr/` | 编号递增、只增不改；推翻旧决策写新篇并注明取代关系 |
| 架构设计 | `docs/architecture/` | 描述“系统是什么、约束是什么”；与实现偏差即修订 |
| 阶段详细设计 | `docs/design/phase-N/` | 每阶段实现前定稿 |
| 路线图 / 阶段文档 | `docs/roadmap/` | 阶段范围/验收；状态以 `00-roadmap.md` 为准 |
| 规范 | `docs/standards/` | 违反要么改正、要么先改规范（走 ADR）；复查见 standards/09 |
| 调研 | `docs/research/` | 事实与数据沉淀；新调查追加新篇，不改旧篇结论（可加“更新”节） |
| 术语表 | `docs/glossary.md` | 面向非技术读者；新术语先登记 |

## 4. 写作要求

- 语言：中文（代码块、标识符、路径、外部 API 名除外）；面向所有者的文档避免未解释的行话。
- **流水账禁令**：docs 内禁止追加式日志（会话记录、每日进展）；唯一流水账是根目录 `CHANGELOG.md`。过程笔记进 `.agents/`。
- 图：架构与流程用 mermaid 内嵌；不引用无法离线查看的外链图。
- 模板（阶段设计稿）：背景 / 目标 / 方案 / 数据与接口定义 / 验收 / 风险 / 待决问题。
- 每篇 ≤300 行（ADR ≤100，phase 设计 ≤500，见 standards/08）。
- 新增文档必须登记 `docs/README.md`；禁止孤儿文档。

## 5. 事实与引用

- 外部事实必须标注来源与日期（仓库/文档/实测）；不把博客或摘要当合同。
- 代码路径、命令、版本号必须可复核；不确定的写“待核实”，不编造。
- 引用参考项目时，明确“只读思路”还是“依赖使用”；GPL/LGPL 项目不得复制文字或代码。

## 6. 附录：《阶段进度报告》模板（存 `docs/design/phase-N/report.md`）

```markdown
# Phase N 阶段进度报告（写给非技术读者）
- 日期：
- 本阶段目标（一句话）：
- 完成了什么（3~5 条，无行话）：
- 验收场景执行结果（逐条：通过/未通过 + 一句说明）：
- 接缝核对（architecture/03 各条）：
- 体量核对（standards/08：docs / .agents / 代码 / 依赖，附豁免清单）：
- 规范复查（standards/09 四问：漏洞 / 过严 / 过松 / 冗余矛盾，逐篇结论）：
- 已知问题与风险：
- 对下阶段的影响：
- 文档更新清单：
```
