# 调研 04：治理参考仓库 Timo-pi

- 状态：定稿
- 日期：2026-10-28
- 关联：ADR-0006；docs/README.md；standards/01 ~ 09

> 参考对象是同一所有者体系下的 Rust 桌面项目 Timo-pi。本文只吸收**治理结构与工作方法**，不复制其代码或技术选型。

## 1. 它做对了什么

| 做法 | 解决的问题 | 本项目采纳 |
|---|---|---|
| `docs/` 单一事实来源 + 文档地图 | 文档散落、孤儿页、状态不明 | 是 |
| 每篇文档带状态/日期/关联 | 不知道能不能开工 | 是 |
| ADR 编号递增、只增不改 | 决策只存在对话里、反复翻案 | 是 |
| 9 篇规范（结构/Git/文档/代码/测试/安全/AI/体量/复查） | 靠人自觉、标准漂移 | 是（按 Go 改写） |
| 路线图唯一看板 + 阶段文档 | README 变成流水账 | 是 |
| CHANGELOG 唯一追加流水、面向非技术读者 | 所有者读不懂技术细节 | 是 |
| 阶段验收 + 进度报告 + tag | “做完了”没有客观标准 | 是 |
| `.agents/` 交接卡 + handoff + pitfalls + skills | 会话失忆、重复踩坑 | 是 |
| 硬预算（文档/知识库/代码/依赖/构建产物） | 无限膨胀 | 是（Go 版） |
| 规范复查（漏洞/过严/过松/矛盾） | 规范本身腐化 | 是 |
| 外部代码许可证纪律 | GPL/LGPL 污染 | 是（更严格） |

## 2. 它踩过的坑（对本项目有直接价值）

- **把上游摘要当合同**：文档写的 API 与真实源码不一致。→ 本项目要求关键事实回到源码/实测，research 标注依据。
- **依赖解析成功 ≠ API 兼容**：升级必须编译 + 测试，不只看版本号。→ 内核/MyGo 升级独立提交、全量测试。
- **Windows 下 bash 可能是 WSL**：脚本行为与预期不同。→ 本项目脚本以 Go/跨平台工具为主，bash 脚本只用于 CI 与本地门禁，并注明环境。
- **子进程 kill 后孙进程仍握着管道**：读取必须有界。→ 插件子进程必须清理进程树、读取有超时与上限。
- **覆盖层焦点陷阱**：模态会屏蔽根级快捷键。→ 桌面插件契约里明确焦点与快捷键归属。
- **半行追加/崩溃安全**：日志与会话写入要能恢复。→ 会话交给上游；本项目日志用追加 + 截断检测。
- **构建缓存无限增长**：Rust target 达到数十 GB。→ Go 构建缓存不在仓库；本项目的体量预算重点转向 docs、二进制与前端资产。

## 3. 不采纳的部分

| 项 | 原因 |
|---|---|
| Rust / gpui-kit / NSH 技术栈 | 本项目是 Go + MyGo |
| Cargo 门禁与 `target/` 容量治理 | Go 的构建缓存与产物形态不同；改为 Go 门禁与资产预算 |
| 具体的阶段编号与内容 | 本项目按 M0~M6 重新划分 |
| 其 `ponytail` 技能文本 | 不复制第三方文本；需要时以本项目规范表达同样纪律 |
| 其 ADR 结论 | 技术前提不同，不能直接套用 |

## 4. 借鉴的写作风格

- 先结论、再理由、再备选与后果；不写“可能/也许”式空话。
- 术语第一次出现给解释或链接术语表。
- 验收场景用非技术语言，逐条可打勾。
- 风险写“等级 + 对策”，不隐藏坏消息。
- 文档覆盖式更新；历史靠 git，不靠文内追加日志。

## 5. 本项目的差异

- **内核是外部依赖**：多一层“上游钉版本 + 封装隔离”的治理。
- **插件跨进程**：多一套协议、生命周期与安全审计规范。
- **双渲染路径**：文档必须明确“哪个界面走哪条路径”，避免实现时反复。
- **新建仓库**：Phase 0 一次性建立全部基线，而不是逐阶段累积。

## 6. 结论

Timo-pi 的治理结构可以直接复用；技术内容必须重写。最重要的不是文件数量，而是三条纪律：**文档先行、决策留痕、每轮收尾沉淀**。
