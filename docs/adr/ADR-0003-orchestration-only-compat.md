# ADR-0003：只兼容编排型扩展，TUI 调用在适配层拒绝

- 状态：定稿
- 日期：2026-10-28
- 关联：architecture/03、04；research/02

## 背景

pi 的扩展是 TypeScript，能力面包含工具/命令/事件钩子，也包含 `ctx.ui.*`、`registerShortcut` 这类终端界面能力。桌面端没有终端语义；逐条翻译 TUI 组件既昂贵又注定失真。

## 决策

按能力分类处理：

| 扩展面 | 桌面策略 |
|---|---|
| 工具注册、命令注册、事件钩子、子代理、workflow、异步编排 | 兼容（A 轨） |
| `ctx.ui.*`（overlay、select、input 等） | 拒绝，返回 `ErrUIUnsupported` 与一次性诊断 |
| `registerShortcut` | 拒绝；快捷键归宿主 |
| 纯数据/配置型扩展 | 兼容 |
| 终端主题、渲染器 | 丢弃 |

拒绝必须**结构化、可诊断、不致命**：插件其他能力继续工作，UI 告知“该插件请求了桌面不支持的能力”，桌面用原生插件展示等价信息。

## 理由

- 编排逻辑与终端无关，复用价值高；TUI 渲染与桌面交互模型不兼容，翻译成本高且体验差。
- 明确边界比“尽量兼容”更可维护：插件作者能预期行为，宿主不会陷入模拟终端的泥潭。
- 桌面端可以用更好的形式呈现同一信息（树、时间线、Diff）。

## 备选（否决）

- **全量兼容（含 TUI 模拟）**：等价于在桌面里跑一个终端模拟器，违背项目目标。
- **完全不兼容扩展**：放弃 pi 生态中最有价值的编排能力。
- **静默忽略 UI 调用**：插件会以为界面已显示，产生不可预测行为；必须显式拒绝。

## 后果

- 需要本项目自建 A 轨适配器（`sky-valley/pi` 没有 extensions runtime）；Phase 2 先做协议与过滤，Phase 6 决定桥接还是重写。
- 需要一个“能力诊断”UI，让用户看懂哪些插件被降级。
- 文档必须明确：**不支持**终端界面扩展；不要用“完全兼容 pi 插件”做宣传。
- prompt templates 同样暂缺，不能算作已支持能力。
