# ADR-0010：单人开发期允许直接提交 main

- 状态：定稿
- 日期：2026-10-28
- 关联：standards/02 §1；standards/09 §4；ADR-0006

## 背景

standards/02 规定“一切变更经 feature 分支合并入 main，禁止直接 push”，其前提是有评审与 CI 门禁。当前仓库只有一名人类所有者，没有第二双眼睛，也没有 CI；Phase 0~2 实际一直直接提交 `main`。Phase 2 验收报告已把这条偏差列为待所有者决定项。

所有者决定：承认现状，改成“单人开发例外”，而不是继续违规或引入空转的分支仪式。

## 决策

在**单人开发期**（一名人类所有者、无 CI、无外部评审）允许直接提交并推送 `main`，同时保留以下硬约束：

1. 每个提交只做一件可描述的事；提交信息仍用 Conventional Commits。
2. 推送前必须跑完整门禁：`gofmt -l .`、`go vet ./...`、`go test -race ./...`、`bash scripts/check-docs.sh`；任一失败不得推送。
3. 阶段里程碑仍打 annotated tag（`phase-N.start` / `phase-N.end`），tag 信息写一句验收结论。
4. 已推送历史禁止 force-push；回滚用 `git revert`。
5. 一次变更跨越多日时，可以临时开分支自用，合并方式不限，但不得据此跳过门禁。

## 触发回到分支模型的条件（任一成立）

- 出现第二名人类贡献者，或要求外部代码评审；
- 建立 CI 且要求 PR 绿灯合并；
- 分发签名/发布流程需要受保护分支或审批。

触发后：恢复 standards/02 的 feature 分支规则，并新增 ADR 记录恢复原因。

## 后果

- 减少单人开发的空转成本；`main` 的可靠性由“推送前门禁”而非评审保证。
- 没有 PR 讨论记录；设计取舍仍由 ADR / Phase 文档 / CHANGELOG 留痕。
- 风险集中在“门禁漏跑”：以硬性清单与本地脚本兜底，阶段报告披露执行结果。

## 护栏

- 门禁结果写进阶段报告的“边界”或“规范复查”节，不能只写“跑过了”。
- 破坏性操作（重写历史、删分支、强推）仍需所有者明确同意。
- 若发生一次“门禁全绿但 main 坏了”的事故，按 standards/09 触发复查，评估是否收回本例外。
