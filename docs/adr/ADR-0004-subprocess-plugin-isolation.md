# ADR-0004：第三方插件走子进程 + IPC，不用 Go `plugin` 包

- 状态：定稿（2026-10-28 修订：澄清“进程隔离 ≠ 安全沙箱”）
- 日期：2026-10-28
- 关联：architecture/03、04；research/05

## 背景

插件需要动态加载、可卸载、崩溃隔离与版本独立。Go 标准库的 `plugin` 包只支持 Linux/macOS，不能卸载/重载，要求主程序与插件用完全相同的 Go 版本与编译标志；Windows 不支持。它不适合作为插件生态的基础。

## 决策

- **静态插件**（首批核心插件）：编译进主二进制，启动时注册，无动态加载问题。
- **第三方/动态插件**：独立子进程，通过 JSON-RPC 2.0 over stdio 通信；需要双向流、多语言或更强 schema 时再评估 gRPC。
- 插件 UI 首版只支持**声明式 UI 描述**（宿主渲染）；“插件自有窗口”模式留 backlog。
- 每个插件有 manifest：名称、版本、协议版本、入口、能力声明、资源上限。

## 理由

- 进程隔离带来崩溃隔离、资源上限与可监督的生命周期；它**本身不是权限沙箱**——权限边界必须由宿主 API 白名单、能力闸与（必要时）OS 级沙箱提供。
- 不绑定 Go 版本/编译器；未来可用其他语言写插件。
- 可强制超时、心跳、重启与审计，符合安全规范。
- 避免 `plugin` 包的平台与运维陷阱。

## 备选（否决）

- **Go `plugin` 包**：平台受限、不可卸载、版本强耦合。
- **宿主内动态执行脚本（JS/WASM）**：安全边界更复杂，且与“桌面插件要画原生界面”目标不符；可作为未来补充，不替代进程隔离。
- **gRPC 作为首选**：引入较重依赖与 proto 工具链；首版 JSON-RPC 足够，保留升级路径。

## 后果

- 需要协议、握手、心跳、超时、重启、日志脱敏与进程树清理的实现与测试。
- 插件开发体验比同进程稍复杂；提供模板与本地调试模式（dev 模式可放宽重启策略）。
- UI 描述模式表达力有限；复杂界面要么提升为宿主原生插件，要么等待“自有窗口”模式立项。
- 单插件默认资源上限：内存 512 MiB、单 RPC 30s、启动握手 10s、心跳 5s；数值可在实现阶段调整并登记。
- **已知限制**：若插件运行时是带原生文件/网络能力的 Node/JS 进程，宿主 API 白名单拦不住 `require("node:fs")` 一类调用；这时只能按“受信任插件”对待，或加运行时/OS 级限制。参考 PI-Desktop 的实现笔记与教训（research/05）。
