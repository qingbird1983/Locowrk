## 背景

用户 2026-10-17 原话（总裁定，逐字引自方案稿的状态头）：

> 「原来我构想的记忆树设想与上下文一体，实际下来不行。记忆这块始终是混乱的。
> 而且记忆实际完全不需要完整的会话上下文，只要记住关键点就行了。
> 最主要的就是各种记忆怎么管理落盘。还有上下文我们现在是用的总结，实际就是压缩，
> 也要参照着怎么调整。不要用总结，也改用压缩。」

定稿前实测到五条根因（只写事实，结论放在下面；逐条的代码级出处由方案稿的 U1–U5 表带着，
本 ADR 不复述读数）：

1. **U1** 组装侧把 `messages` 切到未整理尾巴，断层之前的世界只剩 system 里的 L0 标题加轮级总结；
   v2.141 自己记档的「信息悬崖」是同一件事的症状。
2. **U2** 记忆形态**五套并存**：sqlite KV（`plugins-src/memory-sqlite`）、树章节投影、轮级总结
   （RunSummary）、事实卡（`===FACTS===`）、md 索引原型（`memory_index.rs`）——各有各的读写路径，
   且都自称真源。
3. **U3** 整理管道把整段原文喂给记录员 LLM 换章节与总结，产物仍绑在 `(workspace, session)` 上，
   记忆取材面 = 全量会话。
4. **U4** 真源三处各说各话：机器看 sqlite、人看 md 原型、模型看注入块。
5. **U5** 现役"压缩"其实是记录员 LLM 总结（organize 管线）；机械压缩 ctx-compact 已在 v2.137 整面
   退役、本体删除（`compact.rs` 只剩遗留契约）；工具输出全文进日志进上下文，内核没有任何截断或落盘机制。

约束：会话日志是 append-only 的（内核八条纪律之一，DESIGN 附录 C）；前缀缓存命中率是真实成本项；
北极星是经验标杆——**一个会话窗口里连续工作，不重开会话**（对标实物 Qoder CN 做到，反例 ZCode
阈值不可手设、上下文过 20–30% 后每轮 token 指数级上涨、必须手动压缩才能继续）；单人内测，
不为旧测试残留做兼容承诺；`crates/plugin-api` 是冻结 ABI（改实现可以，改既有对外签名不行）。

## 决策

### 记忆侧

1. **记忆的唯一真源 = md 文件**，布局 `~/.Locowrk/memory/`（全局 `MEMORY.md` + 一事实一文件）与
   `projects/<项目-id>/`（项目索引 + 项目事实）。**不建第二存储、不做双写。**
2. 一事实一文件，类型固定四枚：`user` / `feedback` / `project` / `reference`，按各自的 scope 路由规则
   落全局或项目层；frontmatter 三字段 `name`（kebab-case）/ `description`（一行摘要）/ `metadata.type`；
   `feedback` 与 `project` 正文带 `**Why:**` 与 `**How to apply:**`。
3. **排除清单写进规则**：代码可推导的、git 可查的、AGENTS.md 与 `.Locowrk` 已写的、临时任务状态
   都不配进记忆；用户明说"记住"这类内容也要先反问"哪里令人意外"。
4. **索引常驻、正文按需**：每会话注入全局与项目两份 `MEMORY.md` 的指针行（钳 200 行 / 25KB），
   正文由模型按需读；索引文本会话锁死，人改文件 = mtime 变更 = 显式失效重算。
5. **记忆不从会话派生**。写入面三条通道：现 memory 工具族**改道**成文件操作（save / read / search /
   delete，用户明说"记住 / 忘掉"就立即执行不排队）+ 回合收束后的**增量**抽取（按游标只取上次之后的
   新消息、带前次已产出快照去重、一次性并行写完，"创建零条记忆是正常的"）+ 人直接编辑 md
   （真源唯一后 reconcile 问题自动消失）。
6. **遗忘 = 删文件 + 删索引行**；管理页删除移入 `obsolete/` 做软删，清空 `obsolete/` 才是真删，
   且仍要单独点头。验证只看文件系统：删一条 → grep 数据根零命中 → 下一会话注入块零命中。

### 上下文侧（层序按 2026-10-18 重定：LLM 压缩主位，机械层前置减速 + 护航）

7. **主层 = LLM 深度压缩（compact），缺省开、排首位**。真实 input ≥ 有效阈值就自动触发；动作是把
   较旧对话段交给 LLM 按模板写摘要，摘要以续接框架落断层（"从断点继续、勿复述" + 指回日志路径），
   被摘要段**只出上下文**、日志原文不动（投影替换），近期若干轮原文保留，压到阈值 50% 留缓冲。
   手动「立即压缩」（`/整理` 改语义）当场跑的**就是这个主层**，不是机械档。
8. **机械层是前置减速与保护网，不是替代主层**：落盘（spill，内容超尺寸就写会话附件目录、上下文留
   路径 + 预览，属持续卫生）、微压缩（micro，**先于主层触发**——触发线按参照实现取两式较小者，
   见「后续需要跟进的事项」那条订正，把最旧工具结果清成单行
   占位、保留最近 5 条、设最小节省门槛）、滑窗（slide，**主层熔断打开之后**才用，丢最旧轮次的过程、
   **保留每轮提问**，并在事件里如实记丢弃范围）。微压缩的价值是**推迟并缩小**主层调用（更小的总结面
   = 更便宜的调用），完成上下文重置的仍然是主层。
9. **模板取 OpenCode 的七节工作检查点骨架 + ZCode 的逐字保留规则合成**；防膨胀条款必须随模板走
   （只携带未解决的用户请求、能从代码找回的只留引用、排除会另行注入的内容）；安全约束与用户意图
   **逐字保留**、下一步带原文引用防漂移；"全部用户消息"一节可省（日志全量在库 + 滑窗已机械保留提问）。
10. **失败与应急形状照三家实证补齐**：连续失败熔断 = 3；已爆窗走 overflow 应急档，摘要预算按
    SHRINK_STEPS 递减重试直至成功；含媒体失败降级去媒体重试；压缩模型可配（缺省 = 会话主模型）+
    自定义压缩指令钩子。
11. **阈值 = `min(全局滑杆, 模型窗口封顶)`**：沿用现役 `context.thresholdTokens` 滑杆（100K–800K），
    语义从"整理阈值"改为"压缩阈值"；窗口走现役自动识别链（会话 `context_window` ?? models.dev 目录 ??
    档位 `window_tokens`），输入输出共享窗口、输出侧扣预留；用量尺沿用 v2.138 的真实 input 锚点。
    按模型覆盖阈值留作后续，落点 = 模型管理页。
12. **前缀缓存纪律分两种代价说清**：微压缩边界按 call_id 记账且**单调前进**（清过的不回收），记账落
    `SessionEvent::ContextCompacted`（事件只追加），组装侧重放即得边界 ⇒ 被清前缀逐字节稳定、缓存不
    打断；而**主层每过一次阈值 = 一次性前缀重置**（三家参照同代价，不可避免）。落盘是内容定值判定，
    天然稳定。事件 `strategy` 枚举 = `spill | micro | compact | slide`，复用 `CompactionOutcome` 与
    `estimate_tokens` 这两张现成契约面。
13. **全部数值做成设置项**（可配置原则）：压缩总开关（关 = 完全不压，接近窗口只提醒不动作）、
    深度压缩开关（缺省开）、spill 阈值字符数、微压缩保留条数与触发比例、目标比、压缩模型、
    自定义压缩指令。
14. **会话日志永不被改写**：压缩是组装期的投影，撤销 = 换投影参数重放，事件溯源免费给。这比参照
    产品的"改写 + 决策缓存"形态更干净——我们有 append-only 日志这个它们没有的底座。

### 注入面与退役面

15. 注入块处置：`<persistent_memory>` 退役换成两段索引指针行、`<project_memory_index>` 并进项目索引段
    （同源同物，消灭双出处）、`<environment>` 与 `<repo_context>` 保留不动、`<memory_guidance>` 按新
    工具面与排除清单改写、树目录段随树整体移除。
16. **退役面冻结、不迁移不兼容**：memory-sqlite 插件（存量一次性导出为 md，之后原地保留不读不删）、
    记忆树（投影数据冻结只读、不再生长）、organize 管线、事实卡、树工具族、记忆树看板 UI
    （**整体删除**）。
17. **交接层 `<repo>/.Locowrk/` 改两文档制**：`MEMORY.md` 按主题分节、**原地替换**、每条带日期戳、
    硬顶 200 行 / 10KB；`journal/<YYYY-MM-DD>.md` 按天封卷、昨日不可变。`requirements.md` 保留。
    注入只带 `MEMORY.md`（走 `<repo_context>`），journal 不注入、按需读。目录原则三条原话
    （住仓库、git 排除、宁严勿松）不变，只重定内容形态。
18. **记忆管理页 = Qoder 设置页同款**：三枚行为开关（全局记忆 / 项目记忆 / 项目交接层）各关各的 +
    每层一行（文件数 / 更新时间 / 打开文件夹 / 删除）。**不做应用内记忆列表与详情视图**——
    md 是真源，资源管理器就是查看器。压缩设置另立一页，与记忆页分开。

## 被否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 沿用旧形状调参数（四路信号权重、注入上限、整理阈值） | 问题在形状不在参数，用户已裁定 |
| 双层双写（md 权威 + sqlite 索引，《Memory File-ization Design》v1.0 草案 §8 的推荐形态；该稿 2026-10-18 升 v1.1 时撤销本条） | 双真源正是 U2/U4 的根因；对标实物是 55 个纯文件 + grep 检索，没有机器索引层 |
| 保留记忆树、只换记录员提示词 | 树本身就是 U1 的根因 |
| 上下文**只靠** LLM 总结单层（旧 ctx-compact 单层总结、organize 记录员当唯一手段） | 总结是主层但不是全部：机械前置层与保护网必须同建，否则主层每次触发都拿全量旧段去总结，成本与延迟都压不住 |
| **只做机械层、LLM 深度压缩"预留不建"**（本篇 2026-10-18 首稿的层序） | 用户核对 spec 时以三产品体感 + ZCode / OpenCode 双源码实证推翻：LLM 压缩排首位、最重要，机械层在各家都是无感底层；按旧层序做出来的东西"压不动纯讨论型会话"是必然，而不是待观察的风险 |
| 压缩改写会话日志（对标产品的 replacement 形态） | 我们有 append-only 日志这张底座，投影式压缩保原文、撤销免费 |
| 第一版做 embedding 向量召回 | spec 非目标条：grep 全文 + 索引指针够用，同量级记忆面无向量层 |
| 第一版做后台定期整理通道（"dream" 式） | spec 非目标条：先让回合收束增量抽取跑起来，积弊实测出现再立批，不预造机制 |

## 后果

**正面：**

- 真源只剩一处，`reconcile` 与"三处各说各话"这类问题不是被修好，是**无处发生**（U4 关闭）。
- 遗忘变成可验证的事实而不是承诺：文件不在 = 不在，不会再"重新整理又长回来"。
- 上下文能真正"重置而不重开会话"——这是北极星唯一的承载者；机械前置层把主层触发推后、把总结面
  缩小，于是"连续工作一个窗口"既有重置又不每次都付全额。
- 累计 token 消耗从二次方压回近似线性（AC-11 那条"后半程每轮均值 ≤ 前半程 ×1.2"是可测的），
  阈值可手设 = 用户直接选成本档位。
- 记忆与会话各自可以独立演进；人不经任何 UI 也能权威编辑记忆。
- 压缩是投影 ⇒ 撤销免费、历史重放与实时同形、日志永远是完整底账。

**负面 / 需要接受的代价：**

- 存量数据不承诺兼容：sqlite 只导出一次，树投影冻结只读；被冻结的面在 S4 之前"还能看但不长"。
- 跨会话能力在 S1–S3 的间隙有倒退窗口（风险③）。
- **主层摘要质量是新引入的核心风险面**（LLM 丢料 / 编造），三家参照共同承担、没有更优解；防线是
  三重兜：模板强制逐字保留安全约束与用户意图 + 摘要只是投影不是销毁（日志原文全量在库，可重跑可
  回退）+ 近期原文保留与熔断；机械前置层让主层少触发 = 风险面本身收窄（方案稿「形状侧风险」首条）。
- 每次主层触发 = 一次性前缀缓存重置 = 那一轮实打实多花 token（三家同代价，写在纪律里而不是藏起来）。
- 退役面很大：摘除 memory-sqlite 要同步动 plugin-service 注册面与插件产物清单，属**禁区相邻**，
  动手前单独向人说明；看板 UI 整体删除是不可逆的形态收缩。
- 抽取产出质量（v2.136 有过"无来源加权的自动提取霸榜污染"的教训）；防线是排除清单 + 去重快照 +
  文件制天然可人工清理，且正文不自动注入，污染上限 = 索引一行。

**后续需要跟进的事项：**

- 阶段顺序（每阶段独立可回退、一提交一阶段，开工时每阶段各开一份 spec）：
  **S1 数据面**（文件库布局 + frontmatter/索引读写 + memory 工具改道 + 存量导出 + 管理页改道）→
  **S2 压缩面**（主层深度压缩的模板 / 续接框架 / 熔断 + 落盘 + 微压缩 + 滑窗保护网 + 阈值接线 +
  `ContextCompacted` 复用 + 设置项，可与 S1 并行）→ **S3 注入面**（依赖 S1）→ **S4 退役面**
  （S1+S2+S3 稳定一轮之后）→ **S5 收尾**（authority 五篇重写合一 + ADR 定稿 + roadmap 勾选）。
  本篇即 spec 的 AC-3（已勾）。

## 订正记（2026-10-18，同日）

本篇首稿的**压缩侧层序**写的是「四层全机械、零 LLM，LLM 深度压缩 P5 预留不建、等出现信号再立批」。
这个层序**不是决策人的裁定**：它照的是当时那份文本，而那份文本本身写错了——用户 2026-10-18
核对时指出并当场重定（现行版见方案稿 B 节开头的「排序裁定」段）。本篇相应改动的范围：
决策第 7–13 条重写、被否决方案表新增一行把"只做机械层、LLM 层预留不建"记成**已被推翻的方案**
（这一行是本篇最有价值的部分，因为它就是我自己按错文本写下去的形状）、后果的正负两条随之改写、
标题与文件名里的 `mechanical-compaction` 换成 `llm-compaction-primary`。

为什么改在本篇而不是另开 ADR-0008 取代它：模板那条「ADR 只增不改，决策变了就新写一篇」针对的是
**决策发生变化**，而这里发生的是**记录没跟上决策人的原意**（同一天的定稿纠偏），且本篇提交后尚未
推送、没有任何一行代码或一份文档依赖它——为一条从未成立过的层序留一篇"被取代"的正式记录，会让
ADR 这套东西变成"每篇都可能被自己前一天推翻"，反而降低它的可信度。若决策人认为这条层序变化
本身值得独立留档（它带着 ZCode `policy.ts` / `microcompact.ts` 与 OpenCode `compaction.ts` 三份
实证，确实有独立价值），说一声我就拆成 ADR-0008 并把本篇标被取代。
