# ADR-0008：A 轨运行时在 Phase 2 用 spike 定稿

- 状态：定稿
- 日期：2026-10-28
- 关联：ADR-0003、ADR-0004；architecture/04；roadmap/phase-2、phase-6

## 背景

ADR-0003 现在承诺的是**成员级三分类兼容**（支持/缓做/no-op+诊断），这要求 A 轨能真实执行 pi 扩展的代码并注入 shim。原先计划“Phase 2 只做 mock 协议，Phase 6 再决定桥接还是重写”，但协议错误码、诊断语义、工具注册、UI 降级都依赖运行时能力；拖到 Phase 6 会让前面基于假设的实现返工。

## 决策

在 **Phase 2 内**安排一次**限时 spike（5 个工作日）**，比较三条路线，并在 Phase 2 退出前用新 ADR（ADR-0009）定稿：

| 路线 | 做法 | 主要代价 |
|---|---|---|
| A. QuickJS + 打包 | 安装期用 bundler 把扩展及其依赖打成单文件；宿主内/子进程内 QuickJS 执行；注入 pi shim | 需要打包管线与 shim 维护；Node 内置模块不可用 |
| B. Node 兼容子进程 | 独立进程运行扩展，宿主通过 JSON-RPC 提供 shim API | 需要 Node 运行时与分发；进程边界更清晰 |
| C. Go 重写选定扩展 | 不执行 TS，按语义重写 | 兼容面骤减；只能承诺“编排语义兼容” |

Spike 必须用**一个真实 pi 扩展样本**跑通至少：启动 → 注册一个工具 → 接收一个事件钩子 → 调用一次 `ctx.ui.notify`（映射）与一次 `ctx.ui.setWidget`（no-op + 诊断）。只做“能编译/能加载”不算通过。

## 选择标准（按优先级）

1. 能否真实运行样本扩展，并覆盖 ADR-0003 的矩阵主干。
2. Windows 优先可用；崩溃不影响宿主（子进程隔离）。
3. 安装期打包可复现，运行期不执行 `npm install`、不远程加载代码。
4. 启动时间、内存、长会话稳定性可接受。
5. shim 与打包管线的维护成本；上游 API 变化时的可追性。
6. 许可证与分发约束（不引入 GPL 代码；Node 运行时体积可接受）。

## 理由

- 兼容矩阵已成契约，运行时是它的地基；地基晚定一天，上层就多一天返工风险。
- 三条路线都能做 MVP，但代价差异大；用 5 天实测换掉数周猜测。
- Phase 2 本来就要写协议与 mock，spike 可复用同一套消息与诊断，不浪费。

## 后果

- Phase 2 范围与估时增加（2~3 周 → 3~4 周），但 Phase 6 变成纯接入，总风险下降。
- **ADR-0009 未出之前**：文档与对外表述只能说“计划兼容编排型扩展”，不得说“支持 pi 扩展”。
- 若 A/B 都不达标，选 C，并把 A 轨重新定义为“编排语义兼容”，同时修改 ADR-0003 的矩阵与宣传口径。
- Spike 产物（代码、数据、结论）进 `fixtures/`/`docs/design/phase-2/`，不把试验代码留进生产路径。

## 护栏

- 扩展一律在子进程运行，不进宿主主进程。
- 运行期禁止任意 npm 包安装与远程代码加载；只执行打包产物。
- 安全能力仍按 standards/06 默认拒绝；spike 不得为了跑通样本而放宽。
- 若路线需要 cgo 或破坏 Windows 构建，直接淘汰（standards/04 §1）。
