# ADR-0008：辅助调用有预算，主对话轮的重试仍不设上限

- 状态：已接受
- 日期：2026-10-21
- 决策人：青鸟（原话"辅助调用单独设预算：主对话轮仍不设上限，摘要/压缩这类用户看不见的调用加总时长上限（默认 90s，可配），超时算一次失败、推进熔断计数，3 次后自动压缩停手并如实说「没压成」，主轮继续"）
- 出处：用户报告「**项目会话**在模型推理思考中经常卡死」（2026-10-21 对话）·
  [`specs/12-aux-call-budget`](../../specs/12-aux-call-budget/spec.md) ·
  上一轮裁定见 `llm/retry.rs` 头注「重试不设次数上限（用户裁定"半次失败都不可接受"）」
- 取代：无
- 被取代：无

## 背景

2026-08 定过一条传输韧性规矩：**重试不设次数上限**——瞬时故障一直重试到成功或用户点停止。
它的语境写在 `llm/retry.rs` 头注里：「限流 / 网关抖动 / 断流对用户不可见」「用户裁定
『半次失败都不可接受』」。

这条规矩的落点是**主对话轮**的模型调用（`AppLlm` → `CompatLlm::complete_streaming_with`）：
用户就在旁边看着，一次瞬时抖动重试到成功是想要的。

2026-10-21 用户报了一个现象：**项目会话在模型推理思考中经常卡死**。走查结果是，卡死不在
模型推理本身，而在「自动压缩的摘要调用」这条**辅助路径**上（`llm/aux_client.rs` →
`compact/deep.rs`）。那条路径有三个叠加的性质：

1. 它复用同一个重试环 ⇒ 继承了「不设上限」；
2. 它的 `RetryHooks` 写死 `None` ⇒ **没有停止能力**（用户点「停止生成」停不下来），
   也没有重试通知（界面零反馈）；
3. 压缩挂在 `kernel.step_as` **之前** ⇒ 这段时间界面显示的就是「思考中」，
   而前端的 `st.running` 要等整条 `agent_chat` 兑现才落。

三者叠加 = 一条用户看不见、也停不下来的无限重试挂在对话中间。**熔断（连续 3 次失败就
停手）在这条路径上形同虚设**——熔断计数只在失败**被返回**时推进，而失败永远不返回。

顺带定位出「项目会话为什么更容易」：项目会话多注入一层项目指令链、历史更长、工具输出更大
⇒ 占用更容易越过压缩线 ⇒ 更容易进到这条辅助路径。非项目会话同样会中招，只是触发得晚。

## 决策

**按「用户看得见与否」把重试语义分两档，而不是给全局重试环加次数上限。**

1. **主对话轮不动**：不传预算 ⇒「重试不设上限」逐字保留（用户按「停止生成」能中止它，
   重试前推 `agent://llm-retry` 让前端重置流式缓冲）。判据
   `the_main_turn_keeps_its_unbounded_retry_and_its_stop_hook` 两半都钉。
2. **辅助调用（压缩摘要）有总时长预算**：默认 90s，三档预置（30s / 90s / 300s），
   设置页可调。预算是**总时长**（含全部重试与等待），且**包住单次尝试**——
   只查「重试前累计耗时」不够：一次失败尝试自己就能等满空闲看门狗（180s），
   预算会形同虚设。判据 `an_idle_summary_stream_is_aborted_by_the_budget_not_by_the_idle_watchdog`。
3. **超预算 = 一次失败**（不是空收束）：压缩层据此记一次失败、推进熔断计数；
   连续 3 次后自动压缩停手并如实说「没压成」，主轮继续往下走。
   熔断因此**第一次真的能触发**（判据 `three_failures_fuse_the_auto_compaction_and_stop_further_requests`）。
4. **辅助调用接上停止标记**：用户在等重试与吐字两处都能中止它；停止命中时压缩报
   「已停止」，**不计入熔断失败数**（用户主动停不是失败——记进熔断账的话，停过三次之后
   自动压缩会永久停手，那比卡死更隐蔽）。
5. **辅助调用不推 `agent://llm-retry`**：那个事件会让前端 `resetAssistant` 清空主对话的
   assistant 气泡 ⇒ 制造新回归。摘要重试的可见性改由压缩状态事件承担（刀②）。

## 被否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 全局给重试环加次数上限 | 推翻 2026-08 的裁定，且主对话轮的传输韧性会下降——收益与代价不对等；那条裁定的语境正是「用户就在旁边看着」 |
| 只补界面反馈，不动重试语义 | 用户能看见「没压成」，但**停不下来**这件事还在——最恶劣的性质留着 |
| 把「关掉自动压缩」当长期方案 | 上下文会无限涨到撞窗；那是缓解不是修复 |
| 让摘要改走 `AppLlm::prepare`（复用整条管线） | `prepare` 会应用**会话级模型覆盖** ⇒ 摘要会吃会话的模型/档位，违反既有口径（`aux_client.rs` 的 `session_id: None` 是有意的） |
| 给摘要接 `agent://llm-retry` | 摘要重试会顺手清掉主对话的 assistant 气泡 ⇒ 制造新回归 |
| 摘要失败就硬报错、终止整轮 | 压缩失败不该杀死主任务（上下文压不动 ≠ 任务做不完）；熔断 + 如实告知更合适 |
| 预算耗尽当「空收束」返回 | 压缩层会把半截/空文本当成「摘要写完了」⇒ 记成「摘要不合格」，失败原因也会说错 |
| 用关键词表认「预算耗尽」 | 与既有 `is_overflow_message` 同款先例：判据住在模型接入面，压缩层不自备关键词表；本篇用 `[budget]` 前缀而不是模糊词 |

## 后果

**正面：**

- 「项目会话卡在思考中」这条现象的根因被切断：辅助路径不再有「无限重试 + 停不下来」的组合。
- 熔断第一次真的能触发（它此前依赖「失败被返回」，而失败永远不返回）。
- 主对话轮的传输韧性**逐字未变**（判据两半钉住）。
- 「用户看得见的失败」这条纪律落到辅助路径上：预算耗尽与「模型没答上」「超窗」是三句不同的
  真话，界面能分开说（`[budget]` 前缀 + `llm::retry::is_budget_exhausted` 单一判据）。

**负面 / 需要接受的代价：**

- 大上下文 + 慢模型时，90s 可能不够 ⇒ 摘要被掐掉、这一轮不压。三档预置给了 300s 档，
  但**默认值是我替用户选的**（用户没有依据判断 90s 与 300s 哪个更优）——他随时能改。
- 辅助调用的入参从三个位置参数收成了 `SummaryRequest` 结构体（`model` 与 `session_id`
  都是 `Option<&str>`，位置参数传错编译器不报）。这是本仓第三次因为「两个同型可选参数」
  而收结构体。
- 停止信号现在要穿过辅助调用这条链（`SummaryRequest.session_id` → 停止探针 → 钩子），
  链路上多了一处「归属会话只喂停止标记、不改 `LlmRequest.session_id`」的口径。

**后续需要跟进的事项：**

- ✅ 已兑现（2026-10-21，specs/12 刀①）：预算 + 可中止 + 熔断推进 + 停止不记失败，
  判据 `llm::tests::budget` 四条 + `compact::tests_deep` 两条 + `tests::compact_wiring` 一条。
- ⏳ 待兑现（specs/12 刀②）：自动压缩的**开始**与**失败**在界面推系统条（新通道
  `agent://compact-status`）。改之前自动压缩失败只有 `tracing::debug!` ⇒ 用户看到的
  就是「卡住」而不是「没压成」。`specs/11` 刀⑤ 说的「失败不静默」其实只兑现了日志那一半。
- ⏳ 待兑现（specs/12 刀②）：预算档位的设置面接线（后端读口已在，刀① 落
  `ContextSettings.summary_budget_ms` + 三档校验；前端控件与文案下一刀接）。
- 挂账（另开一刀）：`llm/wire/stream.rs:66-72` 推理优先 `return` ⇒ 同一 chunk 里同时带
  `reasoning_content` 与 `content` 时正文被丢。
- 挂账（另开一刀）：`desktop/src/stores/chat/projection.ts:287` `resetAssistant` 只清
  assistant 气泡、不清 thinking 行 ⇒ 只推过推理就重试时思考内容重复累加。
