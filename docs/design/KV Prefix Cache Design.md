## 1. 设计目标

| 目标 | 含义 |

|---|---|

| **最大化缓存命中率** | 让请求前缀逐字节稳定，命中率目标 > 90% |

| **不增加用户操作** | 缓存机制对用户透明，不需要手动配置 |

| **与现有设计对齐** | 复用 ToolExposure / Session / ctx-compact 的既有能力 |

| **可观测** | 用户能看到命中率，开发者能诊断缓存断裂 |

| **降级安全** | 非 DeepSeek 的 Provider 不依赖此机制，功能不受影响 |

### 非目标

- 不做缓存的手动标记（DeepSeek 是自动识别，不需要 `cache_control` 断点）

- 不做跨用户的缓存共享（每个用户的前缀独立）

- 不做缓存内容的本地存储（缓存由 Provider 侧管理）

## 2. DeepSeek 前缀缓存机制

### 2.1 默认开启，无需修改代码

DeepSeek API 的上下文硬盘缓存技术对所有用户**默认开启**，用户无需修改代码即可享用。每一个请求都会触发硬盘缓存的构建。若后续请求与之前的请求在前缀上存在重复，则重复部分只需要从缓存中拉取，计入“缓存命中”。

### 2.2 严格前缀匹配

缓存匹配的规则是：**从第 0 个 token 开始，逐 token 比对**，找到与之前请求的最长公共前缀。**任何在前缀中间的改动，都会导致该位置之后的所有内容失效。** 不是“相似就能命中”，是“从第一个 token 起完全一致才算命中”。

### 2.3 缓存前缀单元

缓存的最小匹配单位是**缓存前缀单元**。每条缓存前缀是一个独立的完整单元，后续请求只有在**完整匹配**缓存前缀单元时才能命中缓存。

缓存前缀单元在三种时机落盘：

| 时机 | 说明 |

|---|---|

| **请求结束位置** | 每次请求的用户输入结束位置与模型输出结束位置，产生两个缓存前缀单元 |

| **公共前缀检测** | 系统检测到多次请求之间存在公共前缀时，将该公共前缀作为独立单元落盘 |

| **固定 token 间隔** | 长输入/长输出中，以一定 token 数量为间隔截取缓存前缀单元，避免长前缀完全无法被缓存 |

### 2.4 落盘与命中的时序

缓存命中的前提是**相应前缀已被“落盘”**。落盘不是即时完成的——同一个前缀第一次出现时不会命中，需要等到它被落盘之后，后续请求才能命中。

**例一：多轮对话**

```

第 1 轮: [system, user1]

第 2 轮: [system, user1, assistant1, user2]

     ↑ 完整匹配第 1 轮落盘的前缀单元 → 命中

```

**例二：长文本问答（前缀有变化）**

```

第 1 轮: [system, 财报内容 + "总结"]

第 2 轮: [system, 财报内容 + "分析盈利"]    ← 不命中，因为 "总结" ≠ "分析盈利"

第 3 轮: [system, 财报内容 + "收入支出占比"] ← 命中 system + 财报内容 这个公共前缀单元

```

前两次请求不会命中缓存。前两次请求完成后，系统会识别出 `system + 财报内容` 为缓存前缀单元并落盘。第三次请求完整匹配了这个单元，因此命中。

### 2.5 输出随机性不受影响

硬盘缓存只匹配用户输入的**前缀部分**，输出仍然是通过计算推理得到的，仍然受到 `temperature` 等参数的影响。

## 3. 成本杠杆

### 3.1 命中与未命中的价差

以 `deepseek-flash` 为例（空闲时段）：

| 计费项 | 价格（元/百万 token） |

|---|---|

| 输入（缓存命中） | 0.02 |

| 输入（缓存未命中） | 1.0 |

| 输出 | 4.0 |

**缓存命中的输入价格约为未命中的 1/50**。

### 3.2 实际案例

开源 Agent Pi 在 DeepSeek 上达到了约 **99.93%** 的缓存命中率——miss rate 仅 0.07%。Pi 默认只给模型**四个工具**，并且保持**会话仅追加**。报告的影响：约 ¥19 per 1B tokens（有缓存）vs ¥900+（无缓存）——**约 47 倍的输入成本差异，完全由请求组装方式驱动**。

第三方基准测试（Composio）在 8 个 Harness 上跑 DeepSeek V4 Flash：Pi 每个成功任务约 $0.028，Claude Code 约 $0.195——**近 7 倍差距**，同一个模型，不同的 Harness，不同的账单。

### 3.3 成本杠杆总结

| 杠杆 | 缓存友好 | 缓存敌对 |

|---|---|---|

| **工具集** | 少量工具，固定顺序 | 大量工具，每轮重排 |

| **会话** | 仅追加，从不重写历史 | 重写/摘要早期对话 |

| **系统提示** | 静态，无时间戳 | 注入日期、变化的元数据 |

| **中间数据** | 不进入上下文 | 每步重新发送完整工具输出 |

**Locowrk 已有的 `ToolExposure`（最小工具集）和 append-only `Session`（仅追加会话），已经天然是缓存友好的。** 前缀缓存设计要做的是**保护这个优势，不被后续功能破坏。**

## 4. Locowrk 的缓存友好架构

### 4.1 请求前缀的固定结构

缓存命中的核心是**请求前缀逐字节稳定**。Locowrk 的请求前缀必须严格按以下顺序组装：

```

┌─────────────────────────────────────────────┐

│  1. System Prompt（完全静态）                 │  ← 绝对不能变

├─────────────────────────────────────────────┤

│  2. Tool Definitions（工具 schema，固定顺序）│  ← 顺序必须确定

├─────────────────────────────────────────────┤

│  3. Memory Inject Block（会话级预取一次）     │  ← 不在每轮变化

├─────────────────────────────────────────────┤

│  4. 会话历史（append-only）                   │  ← 只追加，不重写

│     ├── user1                                │

│     ├── assistant1                           │

│     ├── tool_call1                           │

│     ├── tool_result1                         │

│     ├── ...                                  │

│     └── user_n                               │  ← 只在末尾追加

└─────────────────────────────────────────────┘

```

**从第 1 到第 3 块，在整个会话内必须逐字节不变。** 只有第 4 块（会话历史）的末尾允许追加。

### 4.2 与 ToolExposure 的对齐

`ToolExposure` 决定本轮暴露哪些工具。**暴露的工具集必须在会话内保持稳定**——如果第 1 轮暴露了 `[fs_read, fs_list, search_tools]`，第 2 轮变成了 `[fs_read, fs_write, search_tools]`，工具定义块就不一致了，缓存从第 2 块起全部失效。

**策略**：

| 场景 | 行为 |

|---|---|

| **会话开始** | 确定工具集，会话内不再改变 |

| **需要新工具** | 通过 `search_tools` 元工具按需拉取，不改变已暴露的工具集 |

| **用户切换权限模式** | 这是显式的会话级变更，接受缓存失效 |

**工具 schema 的顺序必须是确定性的。** 任何重排（按字母、按热度、按随机）都会导致缓存失效。

```rust

/// 工具定义按 plugin_id + tool_name 的字典序固定排序

fn stable_tool_order(tools: &mut Vec<ToolSpec>) {

tools.sort_by(|a, b| {

    (a.plugin_id.as_str(), a.name.as_str())

        .cmp(&(b.plugin_id.as_str(), b.name.as_str()))

});

}

```

### 4.3 与 Session 的对齐

`Session` 已经是 append-only 事件日志。这个设计**天然是缓存友好的**——每轮请求只是在末尾追加新消息，历史部分逐字节不变。

**需要保护的是**：不要让任何功能去“重写”历史消息的字节。

## 5. 必须遵守的工程纪律

### 纪律 1：System Prompt 完全静态

**绝对不能**在 System Prompt 中注入：

- 当前时间戳 / 日期

- 随机 UUID / 会话 ID

- 动态生成的统计数字（如“本轮已用 3 个工具”）

- 变化的用户配置摘要

一个秒级时间戳就能让命中率归零。

**如果确实需要传递动态信息**，放在会话历史中（作为一条 `system` 消息追加在合适位置），而不是放在 System Prompt 里。

### 纪律 2：Memory Inject 会话级预取

**每轮动态检索记忆并注入，是缓存的头号杀手。**

一个真实案例：Mem0 插件每轮把检索记忆注入 system 前缀，命中率约 **1%**；改为“会话级预取一次”后，命中率接近 **100%**。

另一个案例：腾讯 memory-tencentdb 插件向 user 消息开头 prepend 上下文，DeepSeek 命中率从 95.7% 降至 83.3%（-12.4pp），关闭后恢复 93.2%。

**Locowrk 的规则**：

- 记忆检索在**会话开始时执行一次**

- 检索结果作为一个稳定的 block 注入，**会话内不再变化**

- 如果用户显式要求“刷新记忆”，才重新检索并接受缓存失效

### 纪律 3：工具定义块逐字节稳定

工具 schema 的 JSON 序列化必须**逐字节确定**：

- 字段顺序固定（不要用 `HashMap`，用有序结构）

- 不包含任何随机内容

- 浮点数格式固定

- 空数组和 null 的处理一致

### 纪律 4：会话历史只追加，不重写

**任何对已发送历史消息的修改，都会导致从修改位置起的所有缓存失效。**

需要修改历史时（如压缩），必须走专门的压缩路径（见 §6），且压缩后的内容在后续轮次中保持字节不变。

### 纪律 5：时间信息不进前缀

不要把当前时间放进任何进入前缀的内容里。需要时间信息时，放在工具参数中，或者作为一条独立的、不参与缓存匹配的消息。

## 6. 压缩策略与缓存的冲突处理

### 6.1 压缩是缓存的天敌

`ctx-compact` 一旦重写历史，所有缓存失效。**压缩不应频繁触发**，且压缩后的前缀应保持稳定，以尽快重新建立缓存。

### 6.2 分层压缩与缓存边界

借鉴 Waveloom 的四级水位线压缩思路：压缩决策按上下文利用率分级，**压缩后的字节内容永不变化**——一旦某条消息被截断或替换为占位符，它在后续所有轮次中保持完全相同的字节表示，前缀缓存持续命中。

**Locowrk 的对应设计**：

| Tier | 触发条件 | 动作 | 缓存影响 |

|---|---|---|---|

| **Tier 0** | < 60% | 什么都不做 | 无影响 |

| **Tier 1** | 60-80% | 工具结果截断（超长输出替换为摘要 + 截断标记） | 被截断的位置起失效 |

| **Tier 2** | 80-95% | 清除 reasoning / 中间步骤 | 同上 |

| **Tier 3** | ≥ 95% | LLM 增量摘要 | 大范围失效 |

**关键原则**：压缩后的内容**在一次压缩后保持不变**，不要在后续轮次中反复修改。用“单调边界”保证每条消息只被压缩一次。

### 6.3 压缩事件的可观测性

每次压缩写入 `SessionEvent::ContextCompacted`，记录：

```rust

SessionEvent::ContextCompacted {

from_tokens: u64,

to_tokens: u64,

strategy: CompactStrategy,

cache_invalidation_point: usize,   // 从哪条消息开始缓存失效

ts: i64,

}

```

### 6.4 压缩后快速重建缓存

压缩完成后，**接下来的几轮请求应该尽量稳定**，让新的前缀尽快落盘。

**建议**：压缩后触发一个“缓存预热”轮次——发送一个最简请求（只有 system + 最新一条 user 消息），让 Provider 落盘新的前缀单元。

## 7. 可观测性

### 7.1 核心指标

DeepSeek API 在 `usage` 字段中返回两个关键字段：

- `prompt_cache_hit_tokens`：本次请求的输入中，缓存命中的 tokens 数

- `prompt_cache_miss_tokens`：本次请求的输入中，缓存未命中的 tokens 数

**Locowrk 应该在开发者面板中实时展示这两个值。**

### 7.3 缓存断裂诊断

当命中率异常下降时，提供诊断信息：

```

⚠️ 命中率从 96% 降至 12%

可能原因：

• 第 3 轮请求中 system prompt 发生了变化

• 工具定义顺序在第 5 轮被重排

• 第 7 轮 Memory-Inject 注入了新的内容

• 第 9 轮触发了上下文压缩

最近一次完整命中的请求: 第 2 轮

断点位置: 第 2 条消息（system prompt）

```

**诊断的实现**：每轮请求时，将当前请求的前缀与上一轮的前缀做 diff，记录第一个不一致的位置。

```rust

fn diagnose_cache_break(

prev_prefix: &\[Token\],

curr_prefix: &\[Token\],

) -> Option<CacheBreakInfo> {

let first_diff = prev_prefix.iter()

    .zip(curr_prefix.iter())

    .position(|(a, b)| a != b);

// ...

}

```

## 8. 多 Provider 兼容

### 8.1 Provider 的缓存能力差异

| Provider | 缓存机制 | 是否默认开启 |

|---|---|---|

| **DeepSeek** | 硬盘缓存，严格前缀匹配 | ✅ |

| **OpenAI** | 自动前缀缓存（Prompts Caching） | ✅ |

| **Anthropic** | 显式标记 `cache_control` 断点 | ❌（需手动标记） |

| **Ollama** | 无前缀缓存（本地推理无需） | — |

### 8.2 抽象层

在 `LlmService` trait 中加一个缓存能力声明：

```rust

#[async_trait]

pub trait LlmService: Send + Sync {

/// 该 Provider 是否支持前缀缓存

fn supports_prefix_cache(&self) -> bool;

/// 缓存报告字段名（如 "prompt_cache_hit_tokens"）

fn cache_usage_keys(&self) -> Option<CacheUsageKeys>;

async fn complete(&self, req: LlmRequest) -> Result<LlmResponse, LlmError>;

}

pub struct CacheUsageKeys {

pub hit_tokens: &'static str,

pub miss_tokens: &'static str,

}

```

- **DeepSeek**：`supports_prefix_cache() = true`，`cache_usage_keys` 返回 `("prompt_cache_hit_tokens", "prompt_cache_miss_tokens")`

- **Anthropic**：`supports_prefix_cache() = true`，但需要额外的断点标记逻辑

- **Ollama**：`supports_prefix_cache() = false`，不做任何缓存相关处理

### 8.3 缓存友好的请求组装对 Anthropic 的兼容

Anthropic 的缓存需要**显式标记断点**。Locowrk 的请求组装逻辑天然适合：

```

[System Prompt]          ← 断点 1（缓存）

[Tool Definitions]       ← 断点 2（缓存）

[Memory Inject Block]    ← 断点 3（缓存）

[会话历史 - 早期部分]      ← 断点 4（缓存）

[会话历史 - 最近 N 轮]     ← 不标记（每轮变化）

```

**Anthropic 的断点标记不需要改变请求前缀的字节**，只是告诉 Provider“从这里开始缓存”。所以 Locowrk 的静态前缀设计在 Anthropic 上同样有效。

## 10. 常见坑

| 坑 | 原因 | 解法 |

|---|---|---|

| System Prompt 注入了日期 | 动态内容破坏前缀 | 所有动态内容移到会话历史中 |

| 工具顺序随机 | 用了 `HashMap` 迭代 | 用 `BTreeMap` 或显式排序 |

| Memory-Inject 每轮变化 | 每轮动态检索 | 会话级预取一次 |

| 压缩后反复修改 | 没有单调边界保证 | 压缩一次，字节不变 |

| 工具结果原文重放 | 每步重发完整输出 | 旧工具结果用截断后的版本 |

| 缓存命中率突然下降 | 某个功能在改前缀 | 用缓存断裂诊断定位 |

| 不同 Provider 行为不一致 | 没有抽象层 | `supports_prefix_cache` + `cache_usage_keys` |

| 用户切换权限模式后缓存失效 | 工具集变了 | 接受，这是显式变更 |

| 会话 fork 后缓存失效 | 历史前缀变了 | 接受，fork 本质上是新会话 |

## 11. 设计哲学

### 11.1 缓存友好 = 工程纪律

DeepSeek 的前缀缓存不需要开发者做任何事——**但如果不遵守工程纪律，它会悄悄失效**。

一个时间戳、一次工具重排、每轮记忆注入——任何一个都足以让 99% 的命中率跌到 1%。

**缓存友好不是“加一个功能”，是“一组不能违反的纪律”。**

### 11.2 与 LoCo 的契合

Locowrk 的核心哲学是 **Low Cost Communication**。前缀缓存是这个哲学在**成本层面**最直接的兑现：

- **省钱**：命中率 95%+，输入成本降到 1/50

- **省脑**：用户不需要理解缓存机制，只需要享受低成本

- **省心**：开发者面板展示节省金额，用户看得见

### 11.3 与已有设计的协同

| 已有设计 | 对缓存的贡献 |

|---|---|

| `ToolExposure`（最小工具集） | 固定工具前缀 |

| `Session`（append-only） | 历史前缀稳定 |

| `ctx-compact`（分层压缩） | 压缩后字节不变 |

| 静态 System Prompt | 前缀起点稳定 |

**Locowrk 的架构在设计之初就是缓存友好的。** 前缀缓存设计要做的是**保护这个优势，并让它可观测。**

### 11.4 一条判断标准

每做一个新功能，问自己：

> **这个功能会不会改变请求前缀的字节？**

会 → 重新设计，让它在不破坏前缀的前提下工作。

不会 → 放行。

**这条标准应该在每次代码评审时被问到。**
