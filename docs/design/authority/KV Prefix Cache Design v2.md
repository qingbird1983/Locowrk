## 1. 设计目标

| 目标 | 含义 |
|---|---|
| **最大化缓存命中率** | 请求前缀逐字节稳定，命中率目标 > 90% |
| **不增加用户操作** | 缓存机制对用户透明，不需要手动配置 |
| **可验证** | 命中率、节省金额可见——这也是记忆树共存实验（见《Memory Tree Design v2》§11）判定"可行"的仪表 |
| **降级安全** | 非 DeepSeek 的 Provider 不依赖此机制，功能不受影响 |
| **与现有设计对齐** | 复用 ToolExposure / Session / ctx-compact 的既有能力，冲突处给出钉死方案（§4.2） |

### 非目标

- 不做缓存的手动标记（DeepSeek 是自动识别，不需要 `cache_control` 断点；Anthropic 的断点由适配层自动打，见 §8.3）
- 不做跨用户的缓存共享（每个用户的前缀独立）
- 不做缓存内容的本地存储（缓存始终在 Provider 侧，Locowrk 不自管 KV cache）

## 2. DeepSeek 前缀缓存机制

（本节为机制参考，与 v1.0 §2 一致。）

### 2.1 默认开启，无需修改代码

DeepSeek API 的上下文硬盘缓存对所有用户默认开启。每一请求都会触发缓存构建；后续请求与前序请求在前缀上重复的部分从缓存拉取，计入"缓存命中"。

### 2.2 严格前缀匹配

从第 0 个 token 起逐 token 比对，取最长公共前缀。**前缀中间任何改动，该位置之后全部失效。** 不是"相似就能命中"，是"从第一个 token 起完全一致才算命中"。

### 2.3 缓存前缀单元

最小匹配单位是缓存前缀单元，三种时机落盘：

| 时机 | 说明 |
|---|---|
| 请求结束位置 | 每次请求的用户输入结束位置与模型输出结束位置，各产生一个单元 |
| 公共前缀检测 | 多次请求之间存在公共前缀时，将公共前缀作为独立单元落盘 |
| 固定 token 间隔 | 长输入/长输出按一定 token 间隔截取单元，避免长前缀完全无法命中 |

### 2.4 落盘与命中的时序

命中的前提是前缀已被落盘，落盘不是即时的——同一前缀第一次出现不会命中，落盘后后续请求才能命中。多轮对话天然满足：第 2 轮的 `[system, user1, assistant1, user2]` 完整匹配第 1 轮落盘的前缀。前缀中途变化的请求（如换问法）不命中，但系统会识别其中的公共前缀单元落盘，供第三次命中。

### 2.5 输出随机性不受影响

缓存只匹配输入前缀，输出仍受 `temperature` 等参数影响。

## 3. 成本杠杆与缓存经济学

### 3.1 命中与未命中的价差

以 `deepseek-flash` 为例（空闲时段）：

| 计费项 | 价格（元/百万 token） |
|---|---|
| 输入（缓存命中） | 0.02 |
| 输入（缓存未命中） | 1.0 |
| 输出 | 4.0 |

命中价约为未命中价的 **1/50**。

### 3.2 参考案例

开源 Agent Pi 在 DeepSeek 上约 **99.93%** 命中率（默认只给四个工具 + 会话仅追加）：约 ¥19 / 1B tokens（有缓存）vs ¥900+（无缓存）。第三方基准（Composio，8 个 Harness 跑 DeepSeek V4 Flash）：Pi 每成功任务约 $0.028，Claude Code 约 $0.195——同一模型，不同请求组装方式，近 7 倍账单差。

### 3.3 成本杠杆总结

| 杠杆 | 缓存友好 | 缓存敌对 |
|---|---|---|
| 工具集 | 少量工具，固定顺序 | 大量工具，每轮重排 |
| 会话 | 仅追加，从不重写历史 | 重写/摘要早期对话 |
| 系统提示 | 静态，无时间戳 | 注入日期、变化的元数据 |
| 中间数据 | 不进上下文 | 每步重发完整工具输出 |

### 3.4 缓存经济学（v2 新增，统领全文）

1. **已进入缓存前缀的旧内容，后续每轮按命中价计费——约等于免费。**
2. 因此，**清除前缀里的旧内容（截断旧工具结果、收起已展开的记忆、丢弃早期消息）省的是上下文窗口空间，不是钱**；代价是清除位置之后的一次性重命中。清除只在两种情况下值得：腾出的空间能显著推迟下一次大结算（压缩/整理），或冗余内容确实拖累模型质量。
3. **省钱只有两个来源：前缀只追加 + 低频大结算。** 任何"频繁小改前缀"的行为都在烧钱，无论它省了多少 token。

> 定位声明：本文与压缩、记忆收起相关的所有"清理类"功能，都是**空间工具**，不是成本工具。想省钱，答案永远只有 §3.4-3 的两条。

## 4. Locowrk 的缓存友好架构

### 4.1 请求前缀的固定结构

```
┌─────────────────────────────────────────────┐
│  1. System Prompt（静态，stable 段在前）        │  ← 绝对不能变
├─────────────────────────────────────────────┤
│  2. Tool Definitions（请求 tools 字段承载）    │  ← 顺序必须确定，会话内钉死
├─────────────────────────────────────────────┤
│  3. Memory Inject Block（会话级预取一次）      │  ← 不在每轮变化
├─────────────────────────────────────────────┤
│  4. 会话历史（append-only）                   │  ← 只追加，不重写
│     └── ...                                  │
│  ─  消息尾部追加区（时间等每轮变化的动态信息）   │  ← 变化只允许发生在这里
└─────────────────────────────────────────────┘
```

从第 1 到第 3 块，在整个会话内必须逐字节不变；第 4 块只允许末尾追加；**每轮都变的信息只允许追加在第 4 块之后的尾部区**。

### 4.2 工具集会话钉死（ToolExposure 对齐，v2 明确为落地必改项）

**现状冲突**：ToolExposure 按 EWMA 热度 + 检索信号做每轮 Top-N 截断，暴露集逐轮可能变化——tools 块每轮都变，DeepSeek 缓存从 tools 位置起全灭。ZCode 侧实证：工具顺序 = 注册序 + runtime 缓存，同一会话内请求间不变。

**本设计裁定**：暴露集在**会话首次请求时确定，钉死到会话结束**。

| 场景 | 行为 |
|---|---|
| 会话开始 | 确定工具集并缓存于会话侧，后续轮直接复用，不再逐轮重算 |
| 需要新工具 | `search_tools` 元工具按需拉取，不改变已暴露集 |
| 用户切换权限模式 / 中途换模型 | 显式会话级变更，接受缓存失效 |
| 实验对比 | `tools.pinSession` 开关（缺省开，开发者分区），关闭 = 恢复每轮 Top-N 旧行为 |

### 4.3 前缀内部分段与动态信息（v2 新增，ZCode 实证）

- **工具定义只进请求 `tools` 字段，不镜像进 system prompt**——schema 变化不打破 system 前缀，两块独立结算。
- system prompt 内部按 **stable / dynamic** 分段，stable 在前：
  - stable：身份、行为准则、输出规范——整个会话字节不变；
  - dynamic：环境信息（cwd / 平台 / 模型名）、记忆块——**会话内不变、但启动时才确定**的内容排在 stable 之后。
- **每轮都变的信息（当前时间、本轮统计等）不进 system**：作为一条消息追加在历史末尾（尾部追加区）。日期变化、轮次统计都不再是前缀杀手。

### 4.4 与 Session 的对齐

`Session` 已是 append-only 事件日志，天然缓存友好。需要保护的只有一条：**任何功能不得重写已发送历史消息的字节**。需要修改历史时（压缩、整理），走专门的结算路径（§6 /《Memory Tree v2》§7 模式 A），且结算后的内容在后续轮次保持字节不变。

## 5. 工程纪律

### 纪律 1：System Prompt 完全静态

不得在 system prompt 注入：时间戳/日期、随机 UUID/会话 ID、动态统计数字、变化的配置摘要。一个秒级时间戳就能让命中率归零。动态信息进尾部追加区（§4.3）。

### 纪律 2：Memory Inject 会话级预取

每轮动态检索记忆并注入是缓存头号杀手（Mem0 案例：命中率 1% → 会话级预取后接近 100%；memory-tencentdb 案例：prepend 上下文使命中率 -12.4pp）。Locowrk 规则：检索在会话开始执行一次，结果作为稳定 block 注入，会话内不变；用户显式"刷新记忆"才重新检索并接受失效。

### 纪律 3：工具定义块逐字节稳定

schema 序列化字段顺序固定（不用 HashMap）、无随机内容、浮点格式固定、空数组与 null 处理一致；按 plugin_id + tool_name 字典序固定排序；**且只走 tools 字段，不镜像进 system**（§4.3）。

### 纪律 4：会话历史只追加，不重写

任何对已发送历史消息的修改都导致从修改位置起全部失效。修改历史必须走结算路径，且结算后字节永不变化。

### 纪律 5：时间信息不进前缀

需要时间信息时，放工具参数，或作为尾部追加消息。

### 纪律 6（v2 新增）：一次性请求不写缓存

摘要、记录员整理、模型探测等一次性请求，标记 skipCacheWrite——防止一次性前缀污染显式缓存（Anthropic 缓存写入有 1.25× 写入溢价；DeepSeek 自动缓存无此概念，标记无副作用）。在适配层实现，业务零感知。

### 纪律 7（v2 新增）：命中率口径统一

`hit_rate = cache_read / input`，其中 input 为含命中在内的总输入；若某适配层的 input 不含缓存命中，由适配层归一化补齐——**总账必须对得上**。分母不得再加 cache_read / cache_write（ZCode 实测：加了会把命中率整体压低）。

## 6. 压缩策略与缓存的冲突处理

### 6.1 结算是计划内的大失效

任何压缩/整理都使失效点之后全部重命中。这不是要消灭的代价，是要**低频化、计划化**的代价：结算后立即进入稳定期（§6.4），让新前缀尽快落盘。

### 6.2 两种结算形态

| 形态 | 触发 | 定位 |
|---|---|---|
| legacy 分层压缩（现网 ctx-compact） | 利用率阈值 | **空间管理**：Tier 1（60–80%）截断超长工具结果、Tier 2（80–95%）清 reasoning/中间步骤省的是窗口，不省钱（§3.4）；Tier 3（≥95%）LLM 增量摘要才是大结算 |
| 记忆树边界结算（《Memory Tree v2》§7 模式 A） | 用户阈值 + /整理 | 整理 = 一次计划内大失效，之前全程纯追加 |

两形态共存期间按会话二选一（旁车 mode），互不叠加。

### 6.3 单调边界

**压缩后的内容在一次结算后保持不变**，不在后续轮次反复修改。每条消息只被压缩一次，用单调边界保证。

### 6.4 稳定期纪律（v2 替代 v1 的"预热轮"）

v1 §6.4 的"压缩后发送预热请求"**删除**：DeepSeek 自动缓存不需要预热（结算后第一个正常请求自然落盘新前缀，单独的预热请求是多余花费）；Anthropic 显式缓存同样不需要（断点照打即可）。替代为一条稳定期纪律：**结算后的 N 轮内（缺省 3，可调）不再触发任何改前缀的操作**（二次压缩、记忆刷新、工具集变更），让新前缀尽快建立。

### 6.5 压缩事件的可观测性

每次压缩写入 `SessionEvent::ContextCompacted`，含 `cache_invalidation_point`（从哪条消息开始失效），供断裂诊断（§7.4）与结算成本统计。

## 7. 可观测性

### 7.1 数据源（v2 明确：零新增链路）

v2.58 起，每个 LLM step 的 `LlmUsage` 六字段（input / output / cache_read / cache_write / reasoning / total / duration_ms）已随 AssistantMessage 落日志。**命中率统计直接消费 LlmUsage 的 cache_read 与 input，不需要任何新采集。**

### 7.2 指标定义

- 轮命中率 = 本轮 cache_read / 本轮 input（口径见纪律 7）
- 会话累计命中率 = Σ cache_read / Σ input
- 估算节省金额 = Σ cache_read × (未命中单价 − 命中单价)；单价取内置价格表，可在模型配置按 provider 覆盖（价格会变，不写死）

### 7.3 呈现

- **对话区**：上下文用量浮层加一行"缓存命中率 94.7%"（用户可关）。
- **开发者面板**：本轮命中/未命中/总输入、会话累计命中率、累计节省金额、有/无缓存成本对比（实际支出 vs 全按未命中价估算）。

### 7.4 缓存断裂诊断（v2 细化实现锚点；ZCode 明确未做，属 Locowrk 差异化能力）

命中率异常下降时定位断裂点：

- **实现**：对请求前缀做**分块 hash 链**——system hash / tools hash / 记忆块 hash / 逐消息 hash，每轮记录。命中率异常时与上轮 hash 链比对，第一个不一致的块即断裂点。比全量 token diff 便宜一个量级，定位到块已够诊断（"system 变了 / 工具集变了 / 第 k 条消息变了"），无需 token 级精度。
- **开关**：缺省关，开发者分区开启；开启后每轮仅多一次 hash 计算，无额外请求。
- **告警**（可调）：命中率跌破阈值时出记录条/toast，缺省关。

## 8. 多 Provider 兼容

### 8.1 能力差异

| Provider | 缓存机制 | 默认开启 |
|---|---|---|
| DeepSeek | 硬盘缓存，严格前缀匹配 | ✅ |
| OpenAI | 自动前缀缓存 | ✅ |
| Anthropic | 显式 `cache_control` 断点 | ❌（适配层自动打，见 §8.3） |
| Ollama | 无（本地推理） | — |

### 8.2 归一化（v2 简化，废除 v1 的字符串键抽象）

**废除 v1 §8.2 的 `CacheUsageKeys` 字符串键 trait 抽象。** genai 适配层负责把各 provider 的 usage 字段归一化进 `LlmUsage.cache_read / cache_write`（已存在），命中率统计只消费 LlmUsage。Anthropic 断点标记是适配层内部策略，不外露 trait 方法。前缀字节纪律（§4、§5）对自动缓存 provider 就是全部；对显式缓存 provider 再加断点，无需第二套业务逻辑。

### 8.3 Anthropic 断点打法（ZCode 实证，可直接照搬）

- system 的每个 **stable 段末尾**打 `{ type: "ephemeral" }`（缺省 5 分钟 TTL）；
- 组装完成后统一收口：先清掉所有消息级标记，再在**最后一条非 system 消息**上打一个增量锚点；
- 断点不改变任何字节，只声明"从这里起可缓存"——所以 §4 的前缀结构在 Anthropic 上同样有效；
- 一次性请求（摘要/整理/探测）跳过缓存写入（纪律 6）。

## 11. 常见坑

| 坑 | 原因 | 解法 |
|---|---|---|
| System Prompt 注入了日期 | 动态内容破坏前缀 | 动态信息移尾部追加区（§4.3） |
| 工具顺序随机 | HashMap 迭代 | BTreeMap / 显式字典序 |
| **工具集每轮 Top-N 变化（现网 ToolExposure 现状）** | 每轮重算暴露集 | 会话钉死 + `tools.pinSession`（§4.2） |
| 工具 schema 镜像进 system | schema 变更打碎 system 前缀 | 只走 tools 字段（§4.3） |
| Memory-Inject 每轮变化 | 每轮动态检索 | 会话级预取一次（纪律 2） |
| 压缩后反复修改 | 没有单调边界 | 结算一次，字节不变（§6.3） |
| 结算后单独发预热请求 | 多余花费 | 删除预热轮，改稳定期纪律（§6.4） |
| **把清旧工具结果/收起记忆当省钱手段** | 已缓存内容按命中价≈免费 | §3.4 经济学：清旧是空间工具 |
| 一次性请求污染缓存 | 摘要/探测写显式缓存 | skipCacheWrite（纪律 6） |
| 命中率分母加 cache_read/write | 分母口径错 | 纪律 7 |
| 命中率突降无从排查 | 无诊断 | 分块 hash 链断裂诊断（§7.4） |
| 用户切权限模式/换模型后失效 | 显式变更 | 接受 |
| 会话 fork 后失效 | 新前缀 | 接受，fork 本质是新会话 |

## 12. 设计哲学

### 12.1 缓存友好 = 工程纪律

DeepSeek 的前缀缓存不需要开发者做任何事——但如果不守纪律，它会悄悄失效。一个时间戳、一次工具重排、每轮记忆注入，任何一个都足以让 99% 的命中率跌到 1%。缓存友好不是"加一个功能"，是"一组不能违反的纪律"。

### 12.2 与 LoCo 的契合

Low Cost Communication 在成本层面最直接的兑现：省钱（命中率 95%+，输入成本 1/50）、省脑（用户不用理解缓存）、省心（面板展示节省，看得见）。

### 12.3 与已有设计的协同

| 已有设计 | 对缓存的贡献 |
|---|---|
| ToolExposure（会话钉死后） | 固定工具前缀 |
| Session（append-only） | 历史前缀稳定 |
| ctx-compact / 记忆树结算 | 低频大失效 + 单调边界 |
| 静态 system + 尾部追加区 | 前缀起点稳定，变化只发生在尾部 |
| 记忆树（lazy expand） | 展开以工具结果追加，缓存安全 |

### 12.4 两条判断标准

每做一个新功能，先问：

> **这个功能会不会改变请求前缀的字节？** 会 → 重新设计，让它在不破坏前缀的前提下工作；不会 → 放行。

> **这个功能清除已缓存的内容是为了什么？** 为了空间或质量 → 可以做，写清代价；为了钱 → 停，清旧从来不省钱（§3.4）。

第一条应该在每次代码评审时被问到。

### 12.5 数值皆可调

本文所有数值与开关收进 §9 可调项总表，缺省值是建议不是限制（用户裁定）。
