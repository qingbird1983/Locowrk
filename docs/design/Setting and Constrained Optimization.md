## 1. 插件管理：内置插件加禁用

### 问题

截图中，`tool-shout` 有复选框 + `禁用` + `卸载` 三个操作，其余八个内置插件右侧一片空白。

用户**无法禁用内置插件**：
- 不想用 `tool-shell`，关不掉
- 不用 Git，`tool-git` 一直占上下文
- 没配 MCP，`tool-mcp` 一直挂在暴露列表里

### 原因

内置插件是"随仓库分发"的，UI 逻辑默认它们不可操作。

### 改法

| 插件类型 | 操作 |
|---|---|
| **内置插件** | `[禁用]` |
| **第三方插件** | `[☐] [禁用] [卸载]` |

- 内置插件不给"卸载"——它们随程序分发，删了下个版本又回来
- 禁用是**状态切换**，落盘 lockfile 的 `enabled: false`
- 禁用后，插件的所有工具从 `ToolExposure` 候选池移除

### 顺带要确认的

**内置插件的版本策略**：现在 `tool-echo` 是 1.3.0，`tool-shout` 是 1.1.0，版本号独立。将来 Locowrk 主程序升级时，内置插件版本怎么处理？

- 方案 A：随主程序一起升（1.3.0 → 1.3.1）
- 方案 B：独立升（插件自己迭代）

**推荐 B**，因为插件的迭代节奏和内核不一样。但要在 manifest 里显式声明 `bundled: true`，让 UI 知道它和第三方插件的区别。

**优先级**：P0（用户自主控制）

## 2. tool-shell：白名单分级 + denylist 审计

### 现状

> 白名单执行（内置 ls/cat/grep/git status，`LOCOWRK_SHELL_ALLOW` 可扩展）；约 50 项 denylist（rm/sudo/curl/powershell…）永远赢、不进审批；管道/命令替换等元字符整条拒绝；无 shell 解析——引号切词后首词直接 spawn；轮询超时 20s（上限 120s）kill、输出限长。一律 Irreversible。

**做得对的**：
- 白名单 + denylist 双保险
- 无 shell 解析（引号切词后首词直接 spawn）——从根上消灭 shell 注入
- 元字符整条拒绝

**需要改的**：

### 2.1 副作用分级：一律 Irreversible 会引发审批疲劳

**问题**：`ls` / `cat` / `grep` / `git status` 全部走审批。用户点第一次"同意"，第二次，第十次——**闭着眼点同意**。审批变成安全表演。

**改法**：白名单内部按副作用分级。

| 命令 | SideEffect | 说明 |
|---|---|---|
| `ls` / `cat` / `grep` / `git status` / `git log` / `git diff` | **`Pure`** | 只读，自动放行 |
| `git branch` / 其他白名单写操作 | `Irreversible` | 走审批 |
| denylist 命中 | **直接拒绝** | 不进审批 |

**前提**：`fs_*` 的 workspace 守卫修好（见上一轮 fs_read 越界问题）。如果 shell 里的 `cat` 能读到 workspace 外的文件，它不能算 Pure。

**更严谨的**：`Pure` 命令加路径参数校验——参数里出现 workspace 外绝对路径，降级为 `Irreversible`。第一版可以先简单按命令名分级。

### 2.2 白名单匹配粒度：git 需要子命令白名单

**问题**：`git status` 是白名单，那 `git log` / `git diff HEAD~1` 能过吗？

如果只匹配字面 `git status`，用户敲 `git log` 会被拒——而 `git log` 完全无害，用户会疯。

**改法**：`git` 类按"首词 + 子命令"匹配。

```toml
"git" = ["status", "log", "diff", "show", "branch", "remote", "blame"]
```

匹配逻辑：**首词匹配 + 第二词在子命令白名单里 + 参数不再深究**。

对 `ls` / `cat` / `grep` 这类单命令，首词匹配即可。

### 2.3 denylist 审计：补齐"绕过类"命令

**问题**：50 项 denylist 里可能缺了"能绕过白名单"的命令。这些命令本身不算危险，但它们能**间接执行任意代码**。

**必须补的四类**：

**解释器类**（能执行任意代码）：
```
python / python3 / node / bash / sh / zsh / cmd / pwsh
perl / ruby / php / lua
```

**包装类**（能间接执行其他命令）：
```
xargs / env / find（带 -exec）/ nice / timeout / nohup / time
```

**网络类**（能外联，绕过 tool-fetch 的 SSRF 防护）：
```
wget / nc / ncat / netcat / ssh / scp / rsync / telnet / ftp
```

**磁盘/系统类**：
```
dd / mkfs / mount / chmod / chown / chroot / systemctl / taskkill
```

**尤其注意解释器类**：如果用户用 `LOCOWRK_SHELL_ALLOW` 加了 `python`，等于给任意代码执行开了口子。**这几个必须在 denylist 里硬锁。**

### 2.4 冲突处理：`LOCOWRK_SHELL_ALLOW` 和 denylist 冲突

**问题**：用户通过环境变量加了 `rm` 到白名单，denylist 里也有 `rm`。

**改法**：denylist 永远赢，但**必须明确反馈**：
- 启动时检测冲突
- 拒绝加载冲突条目 + 写日志 + UI 里提示

**不能静默失败。** 用户以为"我加了白名单就能用"，实际被静默拦掉——这比明确拒绝更让人困惑。

### 2.5 超时 kill：杀进程组，不是杀单进程

**问题**：`轮询超时 20s kill`——kill 的是子进程还是进程组？

如果只 kill 首进程，它的子进程（比如 `git` 派生的 `git-remote-https`）会变成孤儿进程继续跑。

**改法**：
- **Windows**：用 Job Object，才能杀一整棵树。`TerminateProcess` 只杀一个进程。
- **Linux/Mac**：spawn 时设 `setpgid`，kill 时用 `killpg`。

不做这个，长期运行会有僵尸进程累积。

### 2.6 输出限长：截断而不是拒绝

**问题**：如果输出超限直接拒绝，Agent 会失败，用户看不到任何东西。

**改法**：截断 + 显式标记。

```
... (前面 100KB 已截断)
... (后面还有更多内容，可改用 tail 或指定参数缩小范围)
```

Agent 看到提示，可以自己决定"换个小范围再读"。**比直接失败好得多。**

### 2.7 denylist 里的 rm / sudo / chmod 应该可配置

**这一条见 §3 约束最小化原则。**

现有 denylist 里的 `rm` / `sudo` / `chmod` 是**用户能判断**的操作——他知道自己在删什么。这些应该走审批而不是硬拒。

**改法**：
- 解释器类、包装类、网络类 → **硬锁死**（用户判断不了）
- `rm` / `sudo` / `chmod` / `dd` / `mkfs` → **可配置开关**，默认走审批

**优先级**：P0（安全 + 体验）

## 3. 约束最小化原则（通用）

### 核心原则

> **除了真正致命的操作，一切约束都应提供合理的默认值，并允许用户调整。**
> **即使必须约束，也要保留调整边界的能力。**
> **用户是系统的最终拥有者，不是被保护的对象。**

### 三级分类

| 等级 | 处理方式 | 例子 |
|---|---|---|
| **致命** | 硬编码锁死，不给开关 | ABI 边界、元字符注入、解释器类命令 |
| **高危** | 默认安全，可解锁，红警告 + 二次确认 | 路径根目录、SSRF 内网、危险命令 |
| **其他** | 给合理默认值，随时可调 | 超时、输出限长、Top-N、压缩阈值 |

**"致命"的数量要少到极致。** 每多一个硬编码，都是在替用户做决定，都可能在某个你不知道的场景里拦住了合法需求。

### 判断标准

> **这件事用户自己能不能判断后果？**
> - 判断不了（如 `python -c`）→ 锁死
> - 判断得了（如 `rm`）→ 给开关
> - 需要专业判断（如 SSRF）→ 默认安全 + 红警告可解锁

### 为什么"红警告可解锁"比"硬编码锁死"更好

**理由 1：硬编码会逼用户绕过它。**
用户被硬拦住不能读自己另一个项目目录，他不会觉得"安全"，他会想"这破软件真烦，我去用别的工具"。**硬编码不是在保护用户，是在把用户赶走。**

**理由 2：红警告把责任交还给用户。**
"允许访问内网"这个开关，点下去要经过二次确认，确认框写清楚风险。用户点完，是他的选择，不是软件替他做的决定。

### `tool-shell` 改完后的样子

```
设置 → 命令终端

☑ 启用命令白名单
    白名单命令（每行一条）:
    ls
    cat
    grep
    git status
    git log
    git diff
    [+ 添加命令]

☐ 允许 rm / sudo / chmod 等危险命令
    ⚠️ 开启后，这些命令将进入审批而非直接拒绝

☑ 拒绝管道、命令替换等元字符
    （此选项不可关闭）

超时时间：  [20] 秒（上限 120 秒）
输出限长：  [100] KB

────────────────────

高级（默认折叠）

☐ 允许访问内网地址
    ⚠️ 这会让 Agent 能访问你的本地服务（数据库、管理后台）
       只有在完全信任 Agent 的场景下才开启

☐ 允许访问工作区外的任意文件
    ⚠️ 这会让 Agent 能读取你磁盘上的任何文件
       包括 SSH 密钥、浏览器密码、其他项目代码
```

**关键点**：
- 元字符拒绝**只有说明，没有开关**——唯一"不给选择"的地方
- 危险命令、内网访问、任意文件访问**都给开关**，都带红警告
- 超时、输出限长**直接可调**，不需要警告

### 通用化：所有约束都该按这条原则过一遍

- 上下文压缩阈值 → ✅ 已经是滑条
- 工具暴露 Top-N → 应该可配置（默认 20）
- 每次请求最大工具数 → 应该可配置
- 记忆注入条数 → 应该可配置
- 单个插件最长执行时间 → 应该可配置
- 插件并发数 → 应该可配置
- 会话保留天数 → 应该可配置

**每加一个约束，问自己：这个值，用户会不会想改？**

会 → 给配置项。
不会 → 硬编码，但**在文档里说明为什么**。

**优先级**：P0（贯穿所有后续设计）

## 4. 权限模式（后期）

### 参照设计

截图那个下拉菜单（四个档位）：

```
[完全访问 ▾]  [电脑操作]  [发送]
```

| 档位 | 行为 |
|---|---|
| **计划模式** | 只有 `Pure` 工具放行，写操作全拒 |
| **变更前确认** | `Pure` 放行，`Compensable` 黄色，`Irreversible` 红色 |
| **自动编辑** | `Pure` + `Compensable` 放行，只有 `Irreversible` 弹窗 |
| **完全访问** | 全部放行，只记审计日志 |

### 位置

**会话输入框旁边**的切换器，不是设置里的深层选项。用户随手就能切。

### 关键约束

**硬底线（三类）在任何档位下都生效**，包括"完全访问"。

三类硬底线：
1. **路径逃逸**（`../../.ssh/id_rsa`）
2. **SSRF**（`http://localhost:6379`）
3. **ABI 边界**（插件调内核没暴露的符号）

**"完全访问"不等于"无安全"。** 这是设计的核心。

### 判断标准

> **这件事用户能不能判断？**
> - 判断不了 → 内核直接拦，不弹窗
> - 判断得了 → 弹窗让用户选

### 落地时机

**后期再做。** 现在只做"三类硬底线 + 审批弹窗"，这就够。

**优先级**：P2（后期）

## 5. 设置项归属：上下文窗口移到模型配置

### 问题

截图里"上下文管理"分组下有"模型上下文窗口：262,144 token"。

**归属错了。** `262,144` 是 **DeepSeek 这个模型的属性**，不是"上下文管理"这个功能模块的属性。

放在"上下文管理"里等于**把模型信息抄了一遍**：
- 用户换模型，这个值要跟着变
- 不跟着变，两处就不一致

### 改法

**移到"模型配置"分组：**

```
设置 → 模型配置
  Provider:       [Ollama ▾]
  Model:          [deepseek-flash ▾]
  API Key:        [***]
  Base URL:       [https://api.deepseek.com/v1]
  上下文窗口:     [256K ▾]  ← 自动填充，允许手动覆盖
```

**自动提取来源**：
- Ollama：从 `/api/show` 读 `context_length`
- OpenAI / Anthropic：从内置的模型档案里查
- 读不到才让用户手动填

**"上下文管理"里就不需要这个字段**——它只需要"压缩阈值"和"压缩策略"。阈值是相对于窗口的百分比，不需要知道绝对窗口值。

**优先级**：P1（信息归属）

## 6. 数字呈现规范

### 问题

```
❌ 当前: 20% · 52,428.8 token
❌ 模型上下文窗口: 262,144 token
```

两个层次的问题：

**层次 1：小数没有意义。**
`52,428.8` 的 `.8` 是 `20% × 262,144` 的计算结果，对用户毫无意义——用户不可能去精确到 0.8 个 token。**这个精度是机器算出来的，不是用户需要的。**

**层次 2：数字该按档位显示。**
人脑处理 `64K / 128K / 256K / 512K / 1M` 是"扫一眼就知道"，处理 `262,144` 是"要换算 3 秒"。

### 改法

```
❌ 当前: 20% · 52,428.8 token
✅ 当前: 20% · ≈52K

❌ 模型上下文窗口: 262,144 token
✅ 模型上下文窗口: 256K
```

**更好的呈现：**

```
当前: 20% · ≈52K / 256K
```

`52K / 256K` 的组合让用户一眼知道"我用了五分之一"。这比 `52,428.8 token` 有用得多。

**关键区别**：
- `52,428.8 token` 是"我给你一个数字"——用户要自己算
- `52K / 256K` 是"我告诉你一个比例"——直接把答案给他

### 通用规范

| ❌ 机器语言 | ✅ 人的语言 |
|---|---|
| 262,144 token | 256K |
| 52,428.8 token | ≈52K |
| 102,400 字节 | 100KB |
| 20.0 秒 | 20 秒 |
| 1,048,576 字符 | 1M 字符 |
| 1790770863（时间戳） | 3 天前 |
| 87 个工具 / 20 个暴露 | 已优化 87 → 20 |
| 342ms | 响应稍慢 |

### 规律

- **大数用档位**（K / M / G）
- **小数取整**（不要 `.8`）
- **单位不重复**（不写 `256K token`，写 `256K`）
- **能显示比例就不显示绝对值**

### 这条规范应该写进文档开头

> **数字呈现规范**
> 面向用户的数字，使用人类尺度的档位和取整，不暴露机器精度的原始值。
> 除非这个数字用于精确输入，否则一律使用 K / M / G 等粗粒度单位。
> 能显示比例时，优先显示比例。

**优先级**：P1（体验）

## 7. 通用原则总结

这几条问题是同一个病的不同表现：

| 问题 | 本质 |
|---|---|
| 内置插件不能禁用 | 把用户当被保护对象，而非系统拥有者 |
| tool-shell 一律 Irreversible | 用机器的安全逻辑，而不是用户的使用逻辑 |
| 上下文窗口放错分组 | 信息放错了地方 |
| 52,428.8 token | 信息说错了语言 |

**共同点：让设置页说用户的语言，不是机器的语言。**

三条原则可以立为 Locowrk 的设计纪律：

### 原则 1：约束最小化

> 除了真正致命的操作，一切约束都应提供合理的默认值，并允许用户调整。
> 即使必须约束，也要保留调整边界的能力。
> 用户是系统的最终拥有者，不是被保护的对象。

### 原则 2：信息归属正确

> 每个信息项都应归属于它真正的主语。
> 模型属性放模型配置，功能属性放功能配置。
> 不重复、不抄袭、不一致。

### 原则 3：数字呈现人类化

> 面向用户的数字，使用人类尺度的档位和取整。
> 大数用 K / M / G，小数取整，单位不重复。
> 能显示比例时，优先显示比例。
