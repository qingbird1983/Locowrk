# 环境已知限制

> 长期维护文档。来源：2026-10-06 整轮工具复测（《Tool Layer Issues Todo List》第二节「环境事实」）。
> 用途：所有「外网工具失败 / shell 命令奇怪行为」的排查，**先对照本文，别急着怪工具**。

---

## 限制 1：出站网络非全通

**现象**：国际站点被挡，国内站点可达。

**影响范围**：
- `tool-fetch` 抓国际站点会失败（传输层错误 → 报 Err；4xx/5xx 照常返回正文不算失败）
- LLM 调用境外 API 会失败（llm 兼容层的传输韧性会**无限重试瞬时错误**——境外不可达表现为长时间重试后仍失败，不是快速报错）
- 未来插件市场如果从境外拉取，会失败

**排查口诀**：外网工具失败 → **先怀疑网络，再怀疑工具**。可用 `fetch` 一个国内站 + 一个国际站做二分对照。

**决策记录**：不做代理配置功能（LLM 兼容层 v2.75 裁定同源——网络环境是用户机器的事，应用不替用户选路）。

---

## 限制 2：本机 shell 是 Unix coreutils（无 shell 直 spawn）

**现象**：`rm -rf` 可用，`rmdir /s /q` 不认；`dir` / `del` / `copy` 等 cmd 内建命令不存在。

**根因（代码层）**：`tool-shell` 是**无 shell** 设计——引号感知切词后首词即程序直接 spawn（`exec.rs`），不经过任何 shell。命令按 PATH 解析可执行文件；本机 PATH 里有 Git for Windows 的 `usr/bin`（Unix coreutils），于是：
- `rm` / `ls` / `grep` 解析到 coreutils → Unix 语法可用
- `rmdir /s /q` 解析到 coreutils 的 `rmdir.exe`，`/s` `/q` 被当成路径 → 失败
- `dir` / `del` / `copy` 是 cmd 内建、无对应 exe → 程序不存在

**已落地的缓解**（tool-shell 0.1.3）：`shell` / `shell_read` 双工具描述写明「无 shell 直 spawn + Windows 上 PATH 通常是 Unix coreutils，用 Unix 风格命令；cmd 内建不存在」——模型在工具清单里就能读到，不再靠试错。

**长期排查方向**（单独排期，未排入）：
- PATH 解析的可预期性：不同机器 PATH 差异大（Git 装机选项决定 usr/bin 在不在），描述里的「通常」措辞是如实反映而非含糊
- 跨平台策略候选：宿主显式声明 shell 环境（如检测 Git Bash 并写进工具描述的环境段）/ Windows 命令兼容层 / 均不做维持现状。**当前裁定：维持现状**，等真实使用再评估。

## 排查清单（新增一条前先过一遍）

1. 失败的是不是网络类工具（fetch / LLM / webhook）？→ 先看限制 1
2. 失败的是不是 shell 命令？→ 先看限制 2（是不是 cmd 内建 / Windows 语法）
3. 都不是 → 记进《Tool Layer Issues Todo List》，走工具层排查
