## 1. 设计哲学

### 1.1 捆稻草，不是烧稻草

传统上下文压缩的做法是**摘要**——把一段对话交给 LLM 总结成一段话，用这段话替换原文。这是**把稻草烧了，只留一小撮灰**：灰是浓缩的，但稻草没了；想知道细节，回不去；用户心理上是"它忘了我说的"。

Locowrk 的做法是**捆**——把一段对话**原封不动**留在事件流里，只在上面贴一个标签，把标签放进"目录"。**把稻草捆起来，贴上标签，码进仓库**：稻草一根不少；标签让人快速找到哪一捆；需要时解开看原文；用户心理上是"它记得，只是没展开"。

### 1.2 三条基本原则

**原则 1：原文永不压缩。** 所有对话和工具调用都在 `SessionEvent` 流里，append-only，一个字都不丢。记忆树只是这份事件流的**索引**。

**原则 2：触发由用户控制。** 用户设置一个阈值（滑条，缺省 30%），达到就触发，没达到就不触发。加上 `/整理` 手动命令。没有内部分级，没有"60% 开始、80% 继续"。

**原则 3：切分交给记录员。** 触发之后交给会话记录员（LLM）。它按话题的自然边界切分，粒度随内容重要度变化。闲聊粗切，重要讨论细切。切多少捆、每捆多大，由内容决定，不预设规则。

### 1.3 原则 4（v2 新增）：树是投影，随时可拆

原文在事件流里一个字不动；树坏了删掉重建；方案验证失败，整个投影拆掉重来——**零损失，只花一次整理成本**。这一条是记忆树能与现网体系共存（§11）、能拿真实会话做实验、能随时回退的结构性底气：**验证"记忆树 + 上下文记忆二合一"不需要赌，每一步都可回退。**

### 1.4 一句话

> **不是把稻草烧了，是把稻草捆起来码进仓库。**
> **目录给你，要看哪捆自己翻。**

## 2. 核心模型

### 2.1 原文是源，树是投影

```
┌─────────────────────────────────────────────┐
│  SessionEvent 流（append-only，永不修改）      │
│                                             │
│  #1 user: "帮我看看插件加载慢的问题"           │
│  #2 assistant: "我先看看插件加载逻辑..."       │
│  #3 tool_call: fs_read("plugin-host/...")   │
│  ...                                        │
│  #47 user: "改成静态编译"                     │
└─────────────────────────────────────────────┘
                    ↑ 引用（不复制）
                    │
┌─────────────────────────────────────────────┐
│  MemoryTree（投影，可重新生成）                │
│                                             │
│  root                                       │
│   ├── 捆#1 "插件加载性能问题"   [1, 20]        │
│   ├── 捆#2 "闲聊"             [21, 35]       │
│   └── 捆#3 "改为静态编译"      [36, 47]       │
└─────────────────────────────────────────────┘
```

**关键**：树节点**不存储原文**，只保存 `event_range`。原文永远在事件流里。

### 2.2 三个核心概念

| 概念 | 是什么 | 存储 |
|---|---|---|
| 事件流 | 所有对话和工具调用的原始记录 | append-only 日志 |
| 记忆树 | 事件流的索引，由"捆"组成 | 独立存储，可重建 |
| 消息组装 | 从事件流和树里挑内容，拼成 LlmRequest | 每次请求实时生成 |

## 3. 三层结构

### 3.1 每一捆，三个字段

| 层 | 字段 | 大小 | 生成方式 | 什么时候看 |
|---|---|---|---|---|
| L0 | `title` | ~10 token | 记录员生成 | 默认总览 |
| L1 | `summary` | ~200 token | 记录员生成 | 按需展开 |
| L2 | `event_range` | 0（引用） | 指向原文 | 按需读取 |

**L0 是索引，L1 是概览，L2 是全部。**

## 4. 触发与整理

### 4.1 触发（v2：复用现网滑条 + 手动命令）

- **阈值**：复用现网上下文阈值**滑条**，10–90% 连续可调，缺省 30%。占用 < 阈值 → 不动；≥ 阈值 → 整理未整理尾巴。
- **手动命令 `/整理`**：立即整理当前未整理尾巴，等价于把阈值临时降到当前占用。实验期它是最重要的工具——不用等阈值就能随时检查记录员的产物质量。
- 没有其他内部逻辑，没有隐藏的第二把尺子。

### 4.2 占用锚点（v2 新增）

占用读数**优先取 provider 上报的真实 input tokens**（`LlmUsage`，v2.58 起每步落日志），字符估算只在无真实值时兜底。阈值对用户承诺的是"真实上下文占比"，锚点必须与上下文用量浮层同一口径（ZCode 教训：纯估算不含 tools schema，低阈值下误差占比大）。

### 4.3 整理节奏（v2 新增，可调二档）

| 档位 | 行为 | 适合 |
|---|---|---|
| **批量（缺省）** | 达阈值一次性整理整段尾巴 | 记录员看得全、切分质量好；单次输入大 |
| **增量** | 未整理尾巴每满 X token（缺省 50K）就整理一次 | 记录员单次便宜、树更早可用 |

两档可随时切换；`/整理` 在任一档下都立即整理当前尾巴。**不做绝对假设**：批量 vs 增量没有先验答案，缺省批量（贴近 v1 原设计），实验数据（记录员成本、捆质量）可随时翻案。

### 4.4 交给记录员什么

从"上次整理的位置"到"当前位置"之间的**完整对话**。

### 4.5 记录员做什么

自己判断哪几段是一个话题、哪几段闲聊可粗切、哪几段重要需细切、边界在哪，按语义切分成若干捆。每捆约 10–30K token 是参考范围不是硬规则：闲聊可以一捆 50K，重要讨论可以一捆 5K。**切多少捆由内容决定，不预设数量。**

### 4.6 记录员返回什么

对每一捆输出 `title`（10–20 字名词短语）、`summary`（200 字内，保留关键决策与具体信息）、`event_range`（起止位置）。系统据此建树节点并推进"已整理位置"游标。

### 4.7 例子

300K 对话 `[1-45] 插件性能 [46-52] 闲聊 [53-98] 缓存设计 [99-105] 抱怨进度 [106-120] 部署方案` → 记录员可能切出：捆 1 插件加载性能问题（细）/ 捆 2 中间闲聊（粗）/ 捆 3 缓存设计讨论（细）/ 捆 4 零散对话（粗）/ 捆 5 部署方案讨论（细）。**粒度随内容重要度变化，这就是记录员的价值。**

## 5. 会话记录员

### 5.1 角色定位

独立模型角色，负责整理。与主模型的区别：

| | 主模型 | 会话记录员 |
|---|---|---|
| 职责 | 对话、推理、调用工具 | 整理、切分、起标题、写摘要 |
| 用户感知 | 直接看到 | 后台工作 |
| 质量要求 | 极高 | 够用就行 |
| 速度要求 | 高 | 可以异步 |
| 成本要求 | 相对不敏感 | 极度敏感 |

### 5.2 配置

设置 → 模型配置里一行：**会话记录员 [同主模型 ▾]**。默认不选 = 用主模型；想省钱换便宜的。用户不需要理解"辅助模型""任务路由"，只需要知道有个角色负责记录。

### 5.3 执行方式（异步 + 崩溃恢复）

记录员调用异步：触发 → 创建整理任务投队列 → 立即返回，**对话不等整理**；整理期间该段在树里先放占位标题（"对话 #1-45"），生成完替换。

**崩溃恢复契约（v2 新增）**：整理任务与占位捆随会话持久化；应用重启后在途任务重投；最坏情况 = 整棵树删除重建（原文在事件流里，重跑记录员即可）——这是"树是投影"（§1.3）的兜底：不丢任何数据，只花一次整理成本。

### 5.4 降级策略

| 场景 | 降级行为 |
|---|---|
| 记录员超时 | 重试 3 次（可调），仍失败用规则切分 |
| 记录员返回垃圾 | 校验输出，不合规则用规则切分 |
| 记录员完全不可用 | 用主模型，或规则切分 |
| 用户没配记录员 | 用主模型 |

**规则切分**：按固定 token 数（缺省 20K，可调）机械切分，标题取该段第一条用户消息前 20 字。**实现直接复用现网 ctx-compact 的滑动窗口/切点逻辑**——压缩体系退役后的再就业（§11），不是新代码。

### 5.5 整理反弹熔断（v2 新增，ZCode rapid-refill 教训）

整理完成后 k 轮内（缺省 3）又达到阈值触发 → 记一次"反弹"；连续 m 次（缺省 3）→ 本会话**暂停自动整理**，出系统通知如实告知（手动 `/整理` 不受限）。防止"整理—反弹"死循环烧钱。k、m 进可调项总表。

### 5.6 记录员摘要纪律（v2 新增）

用户在对话里给出的**明确指令与关键决策，必须在其所在捆的 summary 中以引号逐字保留**，不得只留转述。散落在几百轮对话里的"永远用 pnpm 不要用 npm"这类硬约束，是整理最容易稀释、事后最难找回的信息。ZCode 的压缩摘要专设"All user messages 逐字保留"段，同一教训。

## 6. 提示词设计

### 6.1 两层结构

第一层按角色分（主模型 / 会话记录员），第二层按模型身份分（同一角色不同模型提示词不同）：

| 模型 | 特点 | 提示词应对 |
|---|---|---|
| Claude | 对 XML 标签敏感 | `<task>` `<rules>` 结构化 |
| DeepSeek | 中文理解好 | 直接中文描述 |
| Qwen | 偏好简洁指令 | 直说不绕弯 |
| GPT | system prompt 服从度高 | 可放更多规则 |

### 6.2 目录结构

```
prompts/
├── main/     { default.md, claude.md, deepseek.md, qwen.md }
├── recorder/ { default.md, claude.md, deepseek.md, qwen.md }
└── guard/    （未来安全员）
```

匹配逻辑：先找 `{role}/{model_family}.md`，找不到用 `{role}/default.md`。

### 6.3 记录员提示词（通用版骨架）

```markdown
# 任务
你是一个对话整理员。给你一段连续的对话记录，把它整理成若干"捆"。

# 什么是"捆"
一捆是一个完整的话题片段。你自己判断：哪几段讲同一件事应捆在一起、
话题的自然边界在哪、哪些闲聊可粗切哪些重要讨论需细切。
没有固定大小。闲聊可以一捆很多轮，重要讨论可以一捆只有几轮。

# 输出格式
对每一捆输出三部分：
1. title：一句话概括主题，10-20 字，名词短语。
2. summary：200 字以内。包含关键决策和结论，保留具体信息
  （文件名、命令、数字）。不要评价，只记录。
   **用户给出的明确指令和关键决策，必须以引号原文逐字保留。**
3. event_range：这捆对应的对话起止位置。

# 原则
- 按语义边界切分，不按固定长度切分
- 每捆是一个完整话题，不跨话题拼接
- 内容短且不重要可并入相邻捆；没有合适边界宁可粗切不要硬切
```

Claude / DeepSeek / Qwen 版本沿用 v1.0 §6.4–6.6 的差异化写法，各版本统一加入上述**逐字保留**一句。

### 6.4 主模型提示词

沿用 v1.0 §6.7（角色 / 能力含 memory_expand / 原则 / 输出）。

### 6.5 提示词的缓存约束

每个角色的提示词在会话内逐字节稳定：角色提示词独立（主模型与记录员是独立 API 调用，各自缓存互不影响）；会话内不改版本；无动态内容；模型切换 = 接受缓存重置。

## 7. 消息组装

### 7.1 组装结构

```
┌─────────────────────────────────────────────┐
│  [1] System Prompt（静态）                    │  ← 前缀缓存友好
├─────────────────────────────────────────────┤
│  [2] 全局记忆 + 项目记忆（会话预取一次）        │  ← 稳定前缀
├─────────────────────────────────────────────┤
│  [3] 记忆树 · 目录（只显示 L0，只增不改）       │  ← 中段
│       ○ 插件加载性能问题                      │
│       ○ 缓存设计讨论    ...                   │
├─────────────────────────────────────────────┤
│  [4] 未整理尾巴（原文）                        │  ← 后段，保真
├─────────────────────────────────────────────┤
│  [5] 本轮用户消息                             │  ← 尾部追加
└─────────────────────────────────────────────┘
```

### 7.2 尾巴策略（v2 新增，本设计最重要的一个开关，可调二档）

v1.0 的"最近 N 轮完整原文"存在未被察觉的缓存冲突：**窗口每滑一轮，窗口内全部内容字节都变**——稳态下每轮都要按未命中价重付整个窗口段，与《KV Prefix Cache v2》纪律 4 直接打架。v2 把尾巴策略做成显式的二选一：

| 模式 | 尾巴内容 | 缓存行为 | 代价 |
|---|---|---|---|
| **A 边界结算（缺省）** | 自上次整理以来的全部原文 | 两次整理之间组装**纯追加**，前缀缓存全程命中；每次整理 = 一次计划内大失效（等同压缩边界，从目录处重建立） | 上下文占用上限 = 阈值（滑条即尾巴上限） |
| B 固定窗口 | 最近 N 轮（缺省 5，可调） | 稳态下窗口每轮滑动，窗口段每轮重付未命中价（窗口 token × 价差 × 每轮） | 换取更小的上下文占用 |

**模式 A 缺省的理由**：阈值滑条成为唯一需要理解的旋钮（阈值 = 尾巴上限），且与 KV v2 的经济学完全一致。**模式 B 保留为实验档**——不做绝对假设：如果实测小窗口的重命中代价可接受、且更短的上下文带来可感知的质量收益，数据说话再切换缺省。两模式共享：前缀（system/记忆块）静态、目录只增不改、整理是唯一计划内大失效。

### 7.3 一个具体例子（模式 A）

对话已整理到第 110 轮，阈值 30%，当前占用 22%：

```
[System Prompt]
[全局记忆] - 用户偏好 Rust，讨厌过度设计
[项目记忆] - 项目 Locowrk，关键决策：Tauri 2、C ABI 插件
[记忆树目录]
  ○ 插件加载性能问题
  ○ 中间的闲聊
  ○ 缓存设计讨论
  ○ 部署方案讨论
[未整理尾巴]
  user: "部署脚本跑一下"
  assistant: "好了，scripts/deploy.sh …"（含工具调用，原文）
[本轮]
  user: "报错了"
```

目录占 ~100 token 覆盖前 110 轮脉络；尾巴是缓存全绿的原追加段。

### 7.4 组装原则

**越远越压缩，越近越完整。** 前（静态）/ 中（目录，压缩比最高，3 行覆盖几十轮）/ 后（原文保真）/ 尾（本轮）。

## 8. 惰性加载

### 8.1 默认只给标题

模型默认只看到 L0 标题；觉得某捆相关就调用工具展开。

### 8.2 memory_expand（缓存安全语义）

```json
{
  "name": "memory_expand",
  "description": "展开记忆树中的某一捆，获取更详细的内容",
  "schema": {
    "type": "object",
    "properties": {
      "bundle_id": { "type": "string" },
      "level": { "type": "integer", "minimum": 1, "maximum": 2,
                 "description": "1=摘要，2=完整原文" }
    },
    "required": ["bundle_id", "level"]
  },
  "side_effect": "Pure",
  "exposure": "always"
}
```

`level=1` 返回该捆摘要（~200 token）；`level=2` 返回完整原文（~2000+ token）。**展开 = 该内容作为工具结果追加进会话历史——append-only，前缀缓存安全。** 展开过的捆在后续轮次保持可见，随下次整理自然归档。

### 8.3 memory_collapse（v2 重新定位：空间急救工具，缺省不暴露）

收起 = 从已发送历史中移除内容 = **前缀重写 = 一次计划外缓存失效**。它省的是窗口空间，不是钱（KV v2 §3.4）；且模式 A 下尾巴本身受阈值约束、展开内容会随下次整理归档，collapse 的用武之地很小。

**裁定：缺省不暴露该工具**（宁缺勿假）。设置提供开关（缺省关），开启后可配"自动收起最老展开"的占用阈值（缺省 80%）。把它当省钱功能用是常见误区的头号来源（§16）。

## 9. 可追溯性

三个方向：标题 → 原文（`捆#1 → event_range [1,45] → 事件流`）；原文 → 所属捆（反向索引）；子捆 → 父捆 → root。

        self.map.range(..=event_id).next_back().map(|(_, b)| *b)
    }
}

## 10. 向量库的定位与退役

### 10.1 不作为记忆系统本身

**记忆是时序 + 因果 + 结构问题，不是检索问题。** 向量检索把"点"之间的"边"全丢了，检索回来的是碎片。

### 10.2 唯一合法用途：L0 标题模糊匹配（可选，阶段末）

用户问"上次那个关于性能的问题"时，对 L0 标题做 `top_k=5` 模糊匹配。检索的是标题（少、短、假阳性低），不是摘要或原文。**先有结构（树），再用向量辅助查找。** 实现放阶段末可选（§13）。

### 10.3 现网嵌入层的退役（v2 新增，方向性裁定）

记忆召回走"**索引注入 + 懒加载**"路线——ZCode 实证：零向量的纯索引式记忆在生产环境运行良好，description 写清楚，模型自己会按需读。据此：

- 现网 experiences 自动提取与向量检索：**先关缺省、观察一个版本、再决定删除**（开关已有，嵌入缺席 = 智能层缺席，聊天零影响——可降级架构保证退役是拨开关不是动刀）；
- SharedEmbed 基建同时服务 `search_tools` 语义检索，**那部分与记忆无关，退役决策另行做**；
- 记忆树自身从第一天起零向量可工作。

## 11. 与现网体系的共存与迁移（v2 重写，替代 v1.0 §11 废弃清单）

### 11.1 为什么能共存

**树是投影，请求组装也是投影，SessionEvent 流是唯一真相源且 append-only——两套组装读同一份原文，互不感知。** 共存不需要改架构，只需要开关。记忆树 + 上下文记忆二合一是未经真实验证的自主设计，因此路线是：**先共存 → 实验可行 → 逐步剔除**，每一步可回退。

### 11.2 三阶段路线

**阶段 0 · 观测先行（硬前置）**

命中率面板 + `/整理` 命令入口（KV v2 §7 / §10 阶段 0）。没有仪表，"实验可行"无法判定。

**阶段 1 · 影子运行（树只写不接管）**

memory-tree crate 落地：阈值 + `/整理` 触发，记录员异步整理、写树。**请求组装一行不动**——现网会话照常走 ctx-compact + memory-sqlite，树只是并行观察同一场对话并记账。验证：捆的标题/摘要质量（抽查）、记录员成本与延迟、降级路径、崩溃恢复。记忆页以只读形式展示树。

**阶段 2 · 按会话切流（树模式可选）**

会话旁车 meta 记 `organizer: legacy | tree`（新会话可选，缺省 legacy）。树模式会话：**不注册 ctx-compact**，组装走 ContextAssembler（§7）。两个内置护栏：

- 记录员连续失败 → 规则切分接管（§5.4），树会话永不失控；
- 整理反弹熔断（§5.5）。

**实验判据（两模式各攒数据，A/B 说话）**：前缀缓存命中率（含模式 A vs B）；每轮输入 token 成本与节省金额；记录员开销占比（token 与时长）；召回质量抽查（该找到的信息模型找没找到、memory_expand 是否被有效使用）；整理反弹次数。

**阶段 3 · 逐步剔除（数据说了算）**

缺省切 tree；ctx-compact **退役为降级路径**（规则切分复用其实现，不删代码）；experiences/向量关缺省观察一个版本再定去留；memory-sqlite 声明式记忆**长期保留**——树管情景（那次对话说了什么），它管事实（用户偏好与决定），二者正交互补（ZCode 同构：文件记忆与会话摘要两套并行）。老会话按旁车 mode 永久兼容（事件流不可变）。

### 11.3 概念映射（替代 v1.0 的废弃表）

| v1.0 的处理 | v2.0 裁定 |
|---|---|
| ctx-compact **废弃** | **退役为降级路径**（规则切分的实现来源）；阶段 3 之前仍是现网主力 |
| 60/80/95 分级触发废弃 | 维持废弃（用户阈值滑条 10–90 单旋钮） |
| "上下文管理 / 记忆管理"两页合并 | 维持合并；页内分**记忆树（情景）**与**记忆库（事实，memory-sqlite）**两区块 |
| 全局记忆 USER.md / 项目记忆 PROJECT.md | 对接 memory-sqlite 的两个**约定键位**（全局 scope / 项目 scope），ContextAssembler 的记忆块从这里预取——不发明第二套声明式记忆存储 |

### 11.4 项目级对齐（28·A 资产复用）

树按 **(workspace, session)** 存储与隔离；项目级提供**跨会话的 L0 联合视图**（记忆页的项目维度 + §10.2 标题模糊匹配的候选池）。键位与现网 memory-sqlite 的 `(workspace, key)` 隔离同构，子 Agent 无旁车落未归属键位的边界沿用。

## 14. 设计纪律

1. **原文永不修改**：SessionEvent 流 append-only，任何功能不能改写历史事件的字节。
2. **树是投影，可重建**：树随时可从事件流重新生成；树损坏删掉重建；方案失败拆投影重来。
3. **组装保持前缀稳定**：system 完全静态；全局/项目记忆会话内不变；树目录会话内**只增不改**；模式 A 下两次整理之间**纯追加**（尾巴策略 §7.2）。
4. **整理是异步的**：记录员调用不阻塞对话；生成期间用占位捆；崩溃可恢复（§5.3）。
5. **用户可编辑**：每捆标题与摘要用户都能改；用户编辑后标记"手动"，不再被自动覆盖。
6. **不写死分级**：没有 60/80/95，没有"压缩到阈值 50%"。触发就是触发，切分交给记录员。
7. **数值皆可调（v2 新增）**：本文所有数值与开关收进 §15 可调项总表；缺省值是建议，不是限制。

## 16. 常见坑

| 坑 | 原因 | 解法 |
|---|---|---|
| 捆的标题太长 | 记录员没约束 | 提示词明确 10–20 字 |
| 捆的粒度不均匀 | 记录员理解偏差 | 提示词说明"闲聊粗切、重要细切" |
| 树结构太深 | 每次都开新层级 | 限制最大深度 3 层 |
| 用户改了标题后被覆盖 | 重新生成没保留用户编辑 | 编辑后标记"手动"，永不覆盖 |
| 树和事件流不一致 | 并发写没加锁 | 单写者模型 + 事件版本号校验 |
| 记录员超时 | LLM 慢 | 重试 + 降级规则切分 |
| **把 memory_collapse 当省钱工具** | 已缓存内容按命中价≈免费 | 缺省不暴露；定位为空间急救（§8.3 / KV v2 §3.4） |
| **固定窗口模式每轮重付 miss** | 窗口滑动 = 前缀位移 | 缺省模式 A；模式 B 靠数据定去留（§7.2） |
| **批量档单次吞几十万 token** | 低阈值 + 大窗口 | 增量档可调；面板展示记录员成本 |
| **应用被杀丢在途整理** | 队列在内存 | 占位捆持久化 + 重投 + 整树重建兜底（§5.3） |
| **整理—反弹循环烧钱** | 整理后内容快速再膨胀 | 熔断 k/m（§5.5） |
| **用户指令被摘要稀释** | 转述丢细节 | 逐字保留纪律（§5.6 / §6.3） |
| 前缀缓存失效 | 目录每轮都变 | 目录只增不改（纪律 3） |
| 提示词太长 | 想写全 | 记录员任务单一，提示词越简洁越好 |
