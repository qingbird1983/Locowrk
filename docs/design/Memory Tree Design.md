## 1. 设计哲学

### 1.1 捆稻草，不是烧稻草

传统上下文压缩的做法是**摘要**——把一段对话交给 LLM，让它总结成一段话，然后用这段话替换原文。

这就像**把稻草烧了，只留一小撮灰**：
- 灰是浓缩的，但稻草没了
- 想知道细节，回不去
- 用户心理上是"它忘了我说的"

Locowrk 的做法是**捆**——把一段对话**原封不动**留在事件流里，只在上面贴一个标签，然后把标签放进"目录"。

这就像**把稻草捆起来，贴上标签，码进仓库**：
- 稻草一根不少
- 标签让人快速找到哪一捆
- 需要时可以解开看原文
- 用户心理上是"它记得，只是没展开"

### 1.2 三条基本原则

**原则 1：原文永不压缩。**

所有对话和工具调用都在 `SessionEvent` 流里，append-only，一个字都不丢。记忆树只是这份事件流的**索引**。

**原则 2：触发由用户控制。**

用户设置一个阈值。达到就触发，没达到就不触发。没有内部的分级逻辑，没有"60% 开始、80% 继续"。

**原则 3：切分交给记录员。**

触发之后，交给会话记录员（LLM）。它按话题的自然边界切分，粒度随内容重要度变化。闲聊粗切，重要讨论细切。切多少捆、每捆多大，由内容决定，不预设规则。

### 1.3 一句话

> **不是把稻草烧了，是把稻草捆起来码进仓库。**
> **目录给你，要看哪捆自己翻。**

## 2. 核心模型

### 2.1 原文是源，树是投影

```
┌─────────────────────────────────────────────┐
│  SessionEvent 流（append-only，永不修改）      │
│                                             │
│  #1 user: "帮我看看插件加载慢的问题"           │
│  #2 assistant: "我先看看插件加载逻辑..."       │
│  #3 tool_call: fs_read("plugin-host/...")   │
│  #4 tool_result: "..."                      │
│  #5 assistant: "发现问题了，每个 DLL 都..."    │
│  ...                                        │
│  #47 user: "改成静态编译"                     │
└─────────────────────────────────────────────────┘
                    ↑ 引用（不复制）
                    │
┌─────────────────────────────────────────────┐
│  MemoryTree（投影，可重新生成）               │
│                                             │
│  root                                       │
│   ├── 捆#1 "插件加载性能问题"                 │
│   │    event_range: [1, 20]                 │
│   ├── 捆#2 "闲聊"                            │
│   │    event_range: [21, 35]                │
│   └── 捆#3 "改为静态编译"                     │
│        event_range: [36, 47]                │
└─────────────────────────────────────────────┘
```

**关键**：树节点**不存储原文**，只保存 `event_range`。原文永远在事件流里。

### 2.2 三个核心概念

| 概念 | 是什么 | 存储 |
|---|---|---|
| **事件流** | 所有对话和工具调用的原始记录 | append-only 日志 |
| **记忆树** | 事件流的索引，由"捆"组成 | 独立存储，可重建 |
| **消息组装** | 从事件流和树里挑内容，拼成 LlmRequest | 每次请求实时生成 |

## 3. 三层结构

### 3.1 每一捆，三个字段

| 层 | 字段 | 大小 | 生成方式 | 什么时候看 |
|---|---|---|---|---|
| **L0** | `title` | ~10 token | 记录员生成 | 默认总览 |
| **L1** | `summary` | ~200 token | 记录员生成 | 按需展开 |
| **L2** | `event_range` | 0（引用） | 指向原文 | 按需读取 |

### 3.2 三层的信息量级

```
L0:  插件加载性能问题                      ← 10 字
L1:  用户报告插件加载慢，怀疑是 DLL 加载     ← 200 字
     导致。经过排查发现每个插件都静态链接
     了一份公共依赖，造成体积膨胀。建议改
     为共享 runtime。
L2:  [完整对话，从"帮我看看插件加载慢"到    ← 2000+ 字
     "好的，我来改"的 20 轮完整记录]
```

**L0 是索引，L1 是概览，L2 是全部。**

### 3.3 数据结构

```rust
struct MemoryBundle {
    bundle_id: BundleId,
    parent: Option<BundleId>,
    children: Vec<BundleId>,

    // L0
    title: String,
    title_edited_by_user: bool,

    // L1
    summary: String,
    summary_edited_by_user: bool,

    // L2（引用）
    event_range: (EventId, EventId),

    // 元数据
    created_at: i64,
    keywords: Vec<String>,
    token_count: u32,
}
```

**原文不进树。树只记住"我对应哪几条事件"。**

## 4. 触发与整理

### 4.1 触发

**用户设置一个阈值（默认 30%）。**

- 上下文占用 < 阈值 → 不动
- 上下文占用 ≥ 阈值 → 把这段对话交给会话记录员

**没有其他内部逻辑。**

### 4.2 交给记录员什么

从"上次整理的位置"到"当前位置"之间的**完整对话**。

比如 1M 上下文模型，阈值 30%，触发时：
- 上下文里有约 300K token 的对话
- 这段对话打包交给记录员

### 4.3 记录员做什么

**记录员拿到这段连续对话，自己判断：**

- 哪几段是一个话题
- 哪几段是闲聊可以粗切
- 哪几段是重要内容需要细切
- 话题的自然边界在哪里

**然后按语义切分成若干捆。**

每捆大约 10-30K token——这不是硬规则，是参考范围。闲聊可以一捆 50K，重要讨论可以一捆 5K。

**切多少捆由内容决定，不预设数量。**

### 4.4 记录员返回什么

对每一捆，输出：

```json
{
  "title": "插件加载性能问题",
  "summary": "用户报告插件加载慢，怀疑是 DLL 加载导致。经过排查发现每个插件都静态链接了一份公共依赖，造成体积膨胀。建议改为共享 runtime。",
  "event_range": [1, 45]
}
```

**加上起止位置**，系统就能建立树节点，并更新"已整理位置"游标。

### 4.5 一个例子

假设这段 300K 对话的内容是：

```
[1-45]    讨论插件加载性能（重要）
[46-52]   中间闲聊（比如"你吃饭了吗"）
[53-98]   讨论缓存设计（重要）
[99-105]  抱怨进度慢（闲聊）
[106-120] 讨论部署方案（重要）
```

记录员切出来的可能是：

```
捆 1: 插件加载性能问题     event 1-45     (细切)
捆 2: 中间的闲聊           event 46-52    (粗切)
捆 3: 缓存设计讨论         event 53-98    (细切)
捆 4: 一些零散对话         event 99-105   (粗切)
捆 5: 部署方案讨论         event 106-120  (细切)
```

**粒度随内容重要度变化。这就是记录员的价值。**

## 5. 会话记录员

### 5.1 角色定位

**会话记录员是一个独立的模型角色，负责整理对话。**

它和主模型的区别：

| | 主模型 | 会话记录员 |
|---|---|---|
| **职责** | 对话、推理、调用工具 | 整理、切分、起标题、写摘要 |
| **用户感知** | 直接看到 | 后台工作 |
| **对质量要求** | 极高 | 够用就行 |
| **对速度要求** | 高 | 可以异步 |
| **对成本要求** | 相对不敏感 | 极度敏感 |

### 5.2 配置

设置面板里就是一行：

```
设置 → 模型配置

主模型
  [DeepSeek V4 ▾]

会话记录员
  [同主模型 ▾]     ← 默认，不选就是这个
  （可选：换一个更便宜的模型来干整理工作）
```

**用户不需要理解"辅助模型""任务路由"这些概念。** 只需要知道：有个角色负责记录，给他配个模型就行。

**默认不选 = 用主模型。** 用户想省钱可以换便宜的。

### 5.3 执行方式

**记录员的调用是异步的。**

```
主对话流程（同步）
    │
    │ 触发阈值
    ▼
┌─────────────────────┐
│  创建整理任务        │
│  { event_range }     │
└─────────┬───────────┘
          │ 投递
          ▼
┌─────────────────────┐
│  整理任务队列        │
└─────────┬───────────┘
          │ 消费
          ▼
┌─────────────────────┐
│  记录员工作线程      │
└─────────┬───────────┘
          │ 写回
          ▼
┌─────────────────────┐
│  MemoryTree 更新     │
└─────────────────────┘
```

**对话不等整理。** 任务投进队列就返回，用户立刻可以继续对话。整理期间那一捆在树里先放一个占位标题（比如"对话 #1-45"），记录员生成完再替换。

### 5.4 降级策略

记录员可能因为各种原因不可用：网络、配额、宕机。

| 场景 | 降级行为 |
|---|---|
| 记录员超时 | 重试 3 次，仍失败则用规则切分 |
| 记录员返回垃圾 | 校验输出，不合规则用规则切分 |
| 记录员完全不可用 | 用主模型，或规则切分 |
| 用户没配记录员 | 用主模型 |

**规则切分**：按固定 token 数（比如 20K）机械切分，标题取该段第一条用户消息前 20 字。不优雅，但能用。

## 6. 提示词设计

### 6.1 两层结构

```
第一层：角色
  主模型 → 对话型提示词
  会话记录员 → 整理型提示词

第二层：模型身份
  同一角色，不同模型，提示词不同
```

**为什么同一角色还要按模型分？**

| 模型 | 特点 | 提示词应对 |
|---|---|---|
| **Claude** | 对 XML 标签敏感 | 用 `<task>` `<rules>` 结构化 |
| **DeepSeek** | 对中文理解好 | 可以直接用中文描述 |
| **Qwen** | 偏好简洁指令 | 不要绕弯子，直说 |
| **GPT** | 对 system prompt 服从度高 | 可以放更多规则 |

### 6.2 目录结构

```
prompts/
├── main/                    ← 主模型
│   ├── default.md           ← 通用兜底
│   ├── claude.md
│   ├── deepseek.md
│   └── qwen.md
│
├── recorder/                ← 会话记录员
│   ├── default.md
│   ├── claude.md
│   ├── deepseek.md
│   └── qwen.md
│
└── guard/                   ← 未来的安全员
    └── ...
```

**匹配逻辑**：先找 `{role}/{model_family}.md`，找不到就用 `{role}/default.md`。

### 6.3 记录员提示词（通用版）

```markdown
# 任务

你是一个对话整理员。给你一段连续的对话记录，你的工作是把它整理成若干"捆"。

# 什么是"捆"

一捆是一个完整的话题片段。

你要自己判断：
- 哪几段对话在讲同一件事，应该捆在一起
- 话题之间的自然边界在哪里
- 哪些是闲聊可以粗切，哪些是重要讨论需要细切

**没有固定的大小。** 闲聊可以一捆包含很多轮，重要讨论可以一捆只包含几轮。

# 输出格式

对每一捆，输出三部分：

1. **title**：一句话概括主题。10-20 字。用名词短语，不用完整句子。
   例如："插件加载性能问题"、"缓存设计讨论"

2. **summary**：一段话概括这捆的内容。200 字以内。包含关键决策和结论，
   保留具体信息（文件名、命令、数字）。不要评价，只记录。

3. **event_range**：这捆对应的对话起止位置。

# 输出示例

```json
[
  {
    "title": "插件加载性能问题",
    "summary": "用户报告插件加载慢，怀疑是 DLL 加载导致。经过排查发现每个插件都静态链接了一份公共依赖，造成体积膨胀。建议改为共享 runtime。",
    "event_range": [1, 45]
  },
  {
    "title": "一些零散对话",
    "summary": "用户在等待排查结果期间的闲聊。",
    "event_range": [46, 52]
  }
]
```

# 原则

- 按语义边界切分，不按固定长度切分
- 每捆应该是一个完整的话题
- 不要跨话题拼接
- 如果一段内容很短且不重要，可以合并到相邻捆里
- 如果没有合适的话题边界，宁可粗切，不要硬切
```

### 6.8 提示词的缓存约束

**每个角色的提示词，在会话内必须逐字节稳定。**

| 约束 | 说明 |
|---|---|
| **角色提示词独立** | 主模型和记录员是独立的 API 调用，各自缓存互不影响 |
| **会话内不改** | 一旦会话开始，用哪个提示词版本就定了 |
| **无动态内容** | 不注入时间戳、会话 ID、用户信息 |
| **模型切换 = 缓存重置** | 用户中途换模型，提示词变了，接受缓存失效 |

## 7. 消息组装

### 7.1 组装结构

```
┌─────────────────────────────────────────────┐
│  [1] System Prompt（固定，静态）              │  ← 前缀缓存友好
├─────────────────────────────────────────────┤
│  [2] 全局记忆 + 项目记忆                      │  ← 稳定前缀
├─────────────────────────────────────────────┤
│  [3] 记忆树 · 目录（只显示 L0 标题）          │  ← 中段
│       ○ 插件加载性能问题                      │
│       ○ 缓存设计讨论                          │
│       ○ 部署方案                              │
├─────────────────────────────────────────────┤
│  [4] 最近 N 轮完整原文（L2）                  │  ← 后段，保真
├─────────────────────────────────────────────┤
│  [5] 本轮用户消息                             │
└─────────────────────────────────────────────┘
```

### 7.2 组装规则

| 段 | 内容 | 特点 |
|---|---|---|
| **前** | System + 全局/项目记忆 | 稳定不变，缓存友好 |
| **中** | 记忆树目录（L0） | 压缩比最高，3 行覆盖 40 轮 |
| **后** | 最近几轮原文 | 完整保真 |
| **尾** | 本轮消息 | — |

**核心原则：越远越压缩，越近越完整。**

### 7.3 一个具体例子

假设对话已经 120 轮，最近 3 轮保留原文：

```
[System Prompt]

[全局记忆]
- 用户偏好 Rust，讨厌过度设计

[项目记忆]
- 项目 Locowrk，Agent 内核
- 关键决策：Tauri 2、C ABI 插件

[记忆树]

## 8. 惰性加载

### 8.1 默认只给标题

模型默认只看到 L0 标题。如果觉得某捆相关，调用工具展开。

### 8.2 工具定义

```json
{
  "name": "memory_expand",
  "description": "展开记忆树中的某一捆，获取更详细的内容",
  "schema": {
    "type": "object",
    "properties": {
      "bundle_id": { "type": "string" },
      "level": {
        "type": "integer",
        "minimum": 1,
        "maximum": 2,
        "description": "1=摘要，2=完整原文"
      }
    },
    "required": ["bundle_id", "level"]
  },
  "side_effect": "Pure",
  "exposure": "always"

| 调用 | 返回 | 大小 |

## 9. 可追溯性

### 9.1 三个方向

**从标题 → 原文**：`捆#1 → event_range [1, 45] → 事件流第 1-45 条`

**从原文 → 属于哪个捆**：`event#7 → 查索引 → 属于 捆#1`

**从子捆 → 父捆**：`捆#1.1.parent → 捆#1 → root`

### 9.2 反向索引

```rust
struct EventToBundleIndex {
    map: BTreeMap<EventId, BundleId>,
}

impl EventToBundleIndex {
    fn locate(&self, event_id: EventId) -> Option<BundleId> {
        self.map.range(..=event_id).next_back().map(|(_, b)| *b)
    }
}
```

## 10. 向量库的定位

### 10.1 不适合作为记忆系统本身

**记忆是时序 + 因果 + 结构问题，不是检索问题。**

向量检索把"点"之间的"边"全丢了，检索回来的是碎片，碎片之间没有连接。

### 10.2 正确的定位

**向量库只用于一件事：在标题列表里做模糊匹配。**

场景：用户问"上次那个关于性能的问题"，你不记得具体标题。

```rust
let candidates = vector_index.search(query, top_k = 5);
```

**检索的是 L0 标题，不是 L1 摘要，也不是 L2 原文。**

| 特性 | 标题适合 | 原文不适合 |
|---|---|---|
| 数量 | 少（几十个） | 多（几千条） |
| 长度 | 短（10 字） | 长（几百字） |
| 假阳性 | 低 | 高 |

**先有结构（树），再用向量辅助查找。**

## 14. 设计纪律

### 纪律 1：原文永不修改

`SessionEvent` 流是 append-only。任何功能都不能改写历史事件的字节。

### 纪律 2：树是投影，可重建

记忆树可以随时从事件流重新生成。树损坏就删掉重建。

### 纪律 3：组装保持前缀稳定

- System Prompt 完全静态
- 全局/项目记忆会话内不变
- 树目录在会话内只增不改
- 最近原文只追加

### 纪律 4：整理是异步的

记录员调用不阻塞对话。生成期间用占位符。

### 纪律 5：用户可编辑

每一捆的标题和摘要，用户都能改。用户编辑后标记为"手动"，不再被自动覆盖。

### 纪律 6：不写死分级

没有 60/80/95。没有"压缩到阈值的 50%"。触发就是触发，切分交给记录员。

## 15. 常见坑

| 坑 | 原因 | 解法 |
|---|---|---|
| 捆的标题太长 | 记录员没约束 | 提示词里明确 10-20 字 |
| 捆的粒度不均匀 | 记录员理解偏差 | 提示词里说明"闲聊粗切、重要细切" |
| 树结构太深 | 每次都开新层级 | 限制最大深度 3 层 |
| 展开后不收起 | 没有自动回收 | 上下文到阈值时自动收起最老的展开 |
| 用户改了标题后被覆盖 | 重新生成没保留用户编辑 | 用户编辑后标记为"手动" |
| 树和事件流不一致 | 并发写没加锁 | 单写者模型，或事件版本号校验 |
| 记录员超时 | LLM 慢 | 重试 + 降级到规则切分 |
| 前缀缓存失效 | 树目录每轮都变 | 树目录在会话内只追加，不改已有项 |
| 记录员提示词太长 | 想写全 | 记录员任务单一，提示词越简洁越好 |
