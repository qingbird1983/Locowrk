# In-turn Pressure Release Design v1（轮内水位泄压）

状态：**已兑现（v2.193 · 队列 Q8b）**。本稿同时是 Q8c（rule 章节补摘要）与 Q7c（键位合一）的排期依据。
出处：用户真机反馈 2026-10-13 + 后审计队列 Q8 的余量（CB §7.4 只收了工具结果预算层，
水位泄压是它没覆盖的那一半）。

## 1. 用户报的两件事，实际是一件事的一半

原话要点：①「上下文整理会断档、顺序会断」；②「整理触发速度跟不上主模型的产出速度，
导致直接就卡了」，并提议「触发整理时暂停主模型工作，整理完成再自动续上」。

* **①断档 = 已证伪**。双偏移对照（0-based 事件位 vs 1-based 行号）实测 badEdge=0、
  真漏 0；此前"丢了压测结论正文"的判断是把行号当事件位读，已当面收回。断档这条
  不进本批施工面，但**它的自证层**（`memory_expand` 三态文案分家、TOC 跳号标注）
  仍然欠着，记在 Q7c。
* **②跟不上 = 真缺陷，且方向不是"整理太慢"**。真机读数（会话 `desktop-1791871305177`）：
  `context_usage.used = 633,122`、`llm_usage.input = 630,329`、整理阈值 100,000、
  窗口 1,048,576。也就是说**一轮之内的每个 step 都在重发 63 万 token**。整理再快也没用，
  因为现役判定挂在**轮次收束之后**（`after_turn`），而一轮可以有 8 个 step——
  第 2..N 个 step 发出去的时候，轮末那个"更快一点的整理"还没被问过一句话。

结论：**要治的是检查时机，不是执行速度**。用户提议的"暂停主模型等整理"方向对，
但等的是**一次机械切**（毫秒级、不调模型），而不是等一次记录员调用（最坏 90s，
批 Q6 刚把这个数压下来）。

## 2. 取证到的四条硬事实（设计的全部约束来源）

1. `TreeContextSource::plan` 是**每 step** 被内核调用的宿主挂点（`organize/assemble.rs`），
   尾巴起点 = `chaptered_until` ⇒ 想让下一个 step 变轻，只能动游标。
2. `LlmUsage` / `ContextUsage` 每 step 落盘（`runner/mod.rs`），所以 `Organizer::anchor`
   （provider 真实 input，v2.138「进度条 = 触发 = 自动收起」那把尺）在轮内就是现成的水位读数。
3. `rule_split_drafts` 是**纯同步**函数（`memory-tree/manager.rs`），不需要模型、不需要 await。
4. 单写者纪律（§16 / `MemoryTree::insert_placeholder` 的"已有在途 = 拒绝"）：
   在途期不允许第二条通路同时推 `chaptered_until`。

## 3. 三项裁定（用户 2026-10-13）

| 议题 | 裁定 | 落点 |
| --- | --- | --- |
| 施工顺序 | 先堵断档，再治卡 | 断档证伪后本批直接做"治卡"；断档的自证层进 Q7c |
| 泄压形态 | **等一次机械切，摘要后台补** | 本批 = 机械切；摘要补写 = Q8c（见 §5） |
| 数据目录键位 | 现在就一起合并 | 涉用户磁盘、不可逆性质不同 ⇒ 单独一刀 Q7c（先时间戳备份 + 逐条列冲突） |

## 4. 设计

**位置**：`desktop/src-tauri/src/organize/pressure.rs` 的 `Organizer::release_pressure`，
由 `run_turn` 在 **step 边界、`kernel.step_as` 之前**调用（挪到 step 之后 = 救援晚一整步）。

**两个条件同时成立才切**（合取，顺序只影响成本不影响结论）：

1. `should_auto_organize(&inp).is_some()` —— 与轮末那条通路**共用同一个纯函数**与
   同一个 `trigger_input` 装配。批 Q6/Q7 立的口径：不许开第二把尺。
2. `anchor × 100 ≥ window × organize_release_watermark_pct` —— 比较式照 `auto_collapse`
   那一句的形状，锚点同源、零新出处。水位与"该整理"是两件事：前者问"还装得下吗"，
   后者问"该归档了吗"。

**刀口上界 = 本轮开始时的日志长度**（`run_turn` 的 `log_start`）。本轮的事件一条都不许
进章节——正在写的东西被归档 = 模型下一个 step 看不见自己刚说的话，那比超限更坏。
判定用的尾巴（含本轮）与刀口切的区间（不含本轮）是两件不同的事，所以 `build_items`
被叫两次；这不是重复劳动，重复的是"取尾巴切片"这个动作，而那已经收在 `tail_material` 里。

**让位支**：`pending.is_some()`（在途）与 `paused_auto`（熔断）都不切。前者是单写者纪律，
后者与 §8.4「补跑不是绕过熔断的后门」同口径。代价如实：整理在途的最坏 90s 内水位再高
也不切（批 Q6 已从 240s 压到 90s）。

**上限与开关**：`developer.organizeMaxRelease`（0–5 缺省 2，**0 = 关掉本通路**，关掉后
一个字节都不写盘 = 与改前逐字节同形，由测试 `release_cap_zero_writes_nothing_at_all` 钉）
+ `developer.organizeReleaseWatermarkPct`（50–99 缺省 90；上界取 99 的理由：100 等的是
"已经装不下"，而超限报错发生在请求侧）。两条都进设置页 = 可配置原则①②。

**产物与告知**：`build_chapters(.., "rule")` → `apply_organized(.., None)` → 投影落盘 →
`sync_tree_md` → `notify_done(reason = PressureRelease)`。复用 `notify_done` 而不是新建
事件面：它的载荷、`fragments` 置位（下一轮开场告诉模型"历史去哪了"）都是现成的。
前端在同一条 `lw://organize-done` 上按 `reason === "pressure_release"` 分流文案——
必须按 reason 而不是 status，因为泄压的 status 是 `ok`，把它说成"已整理 N 轮"是假告。

**不记反弹**：与 `WindowOverflow` 同族。§5.5 度量的是"整理后占用立刻再超"的烧钱信号，
而泄压是救援。

## 5. 本批刻意不做的两件事

* **摘要后台补（Q8c）**：机械切落的章节标题/摘要来自规则切分（首条用户消息前 20 字），
  补写需要一条"保留 chapter_id 与 title、只换 summary/keywords/token_count"的替换通路
  ——目录行的字节形是 `[id]: [title]`，只换正文不破前缀缓存，这条边界必须先写成判据再动手。
  现役降级支（记录员失败 → 规则切分）**同样**永不补摘要，所以 Q8c 一刀能治两个来源。
  ⚠ 本批文案因此不许出现"摘要稍后补上"那类承诺措辞（已按"摘要从简"落笔）。
* **键位三套合一 + 存量目录合并（Q7c）**：归一 scope_key / 旁车原样串 / 树目录名 / md 项目
  目录名四处不同源，合并要动用户磁盘上的 `~/.Locowrk` 与项目内 `.Locowrk`，性质是不可逆
  数据迁移 ⇒ 与泄压不同刀，须先时间戳备份、逐条列冲突、可回退。

## 6. 判据口径（这一批什么算做完）

1. 时机是跨文件关系 ⇒ 必须有跨文件判据（队列 §6 第 10 条）：`tmp/q8b-shapes.mjs` 的
   S1 组比对 `.release_pressure(` 与 `kernel.step_as(` 的源码次序；变异 **M7 把调用挪到
   step 之后，功能测试与 pnpm build 全绿，只有 S1 红**。
2. `reason` 串是 Rust ↔ 前端契约 ⇒ S3 三处同源（memory-tree / `stores/chat.ts` / 测试断言）；
   变异 **M8 只改前端键位 ⇒ Rust 侧没有任何测试会红**。
3. 同一把尺是纪律而非注释 ⇒ S4 判 pressure.rs 必须调 `trigger_input` + `should_auto_organize`
   且**禁出现自装配的阈值比较**；变异 **M9 换成自写 `anchor < threshold` 后 Batch 档行为等价
   ⇒ 全部用例照绿，只有 S4 红**（这正是"注释里写的纪律"与"有判据的纪律"的差别）。
4. "泄压不等模型"是形状而非愿望 ⇒ S5 判本簇无 `self.client` / 无 `spawn` / 无 `.await`，
   且全部泄压用例跑在同步 `#[test]` 里（异步管道调不动，FakeClient 一律空脚本）。
5. 每条早退理由都要能被区分 ⇒ `Release::Skip(&'static str)` 十条理由，测试按串断言而不是
   只看"返回 0"；其中三条（`empty-slice` / `no-drafts` / `save-failed`）在夹具里造不出来，
   已如实登记为不可造形。
6. 新增一层限制必须自带关掉的路（队列 §6 第 12 条）⇒ `organizeMaxRelease = 0` 的
   "逐字节回到改前"由两条承重：单元测试判投影目录都不被创建，wiring 测试判 `organizer=None`
   时同样零写入。

## 7. 真机走查清单（A–E，交付后由用户现场判读）

* A. 长会话跑到第 3–4 个 step 时，对话区应出现一条「上下文已逼近窗口上限，先把本轮之前的
  历史收起 N 个章节」的系统通知，且**不中断**本轮（不应看到"正在整理"那种等待态）。
* B. 通知之后同一轮继续跑完，本轮刚说过的内容在下一 step 仍可见（模型没有"失忆"）。
* C. 记忆页树面板：这些章节的标题应是首条用户消息前 20 字（规则切分形状），source = rule。
* D. 把 `设置 → 开发者 → 轮内泄压上限` 调 0：同一会话再跑，不应出现任何泄压通知，
  也不应新增章节（这是"关掉就回到改前"的现场版）。
* E. 把水位调到 50 与 99 各跑一次：50 应该更早切、99 应该几乎不切；两种都不该报错。
