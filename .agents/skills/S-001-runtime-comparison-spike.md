# S-001：用同一把尺子做运行时比试

## 适用场景

要在多个运行时（内嵌 JS、独立进程、重写）之间选型，且结论会影响后续架构。ADR-0008 的 spike 就是这种场景。

## 前置条件

- 有一份真实的输入样本，固定版本（全 SHA），不复用生产代码路径。
- 有可量化的及格线/淘汰线（启动、内存、平台可用性、覆盖面、维护成本）。
- 能接受“部分路线被淘汰”的结论，不预设赢家。

## 步骤

1. **定协议再动手**：先写一份最小宿主协议（initialize / event / invoke_tool / metrics / shutdown），三条路线共用。
2. **写一份共享 shim**：每个成员标状态（supported/stub/noop/deferred），用 Proxy 记录“用到但没定义”的成员；这条记录就是覆盖面数据。
3. **样本分两层**：自写探针覆盖必须跑通的最小路径；真实上游样本验证“能不能真跑”。只跑自写探针会高估兼容性。
4. **测量器独立**：启动计时只算到 ready；RSS 多次采样取中位（Go GC 与 V8 堆的稳定时机不同）；一致性检查逐项记录，别只看“没崩”。
5. **同一份样本跨路线跑**：失败也要留读数与错误原文；失败原因是选型证据。
6. **事中记录，事后不补数**：读数落 JSON，报告只引用；未验证项单列，不写成已通过。
7. **把“不能宣传的话”写进结论**：如进程隔离 ≠ 沙箱、某某能力靠 shim 拦不住。

## 验证方法

- 每条路线至少一个“能跑”的样本与一个“跑不动”的样本（或明确的失败点）。
- 淘汰线逐条对照，结论能追溯到具体读数与失败信息。
- 换一台干净机器能按 README 复现。

## 失效条件

- 运行时能力差异不在测量范围（例如只比了启动，没比依赖生态）。
- 样本不具代表性（只用玩具样本，不用真实扩展）。
- 结论先于数据（先定路线再找理由）。
